Policy Delete

1. Overview

Policy Delete is the part of the General Insurance application that removes an insurance policy. It is a chain of three CICS PL/I programs, and the caller passes one shared COMMAREA through all of them.

Program Role Data store touched
LGDPOL01 Front-end dispatcher. Validates the COMMAREA and the request ID, then links to the Db2 delete program. None (no SQL, no file I/O)
LGDPDB01 Deletes the policy row from the Db2 POLICY table. Foreign-key cascade removes the type-specific child row. It then links to the VSAM delete program. Db2 POLICY, plus the ENDOWMENT, HOUSE, MOTOR and COMMERCIAL child tables by cascade
LGDPVS01 Deletes the matching record from the VSAM KSDS policy file. VSAM KSDSPOLY

Four request IDs are supported, one for each policy type:

Request ID Policy type
01DEND Endowment
01DHOU House
01DCOM Commercial
01DMOT Motor

The outcome is reported to the caller only through the two-digit CA_RETURN_CODE field in the COMMAREA. The one exception is a missing COMMAREA, which causes an abend. Failures are logged through the shared utility program LGSTSQ, which writes to a CICS queue (the CSMT transient data queue).

The diagram shows the following:

2.2 Shared COMMAREA Contract

All three programs map the same LGCMAREA layout over the COMMAREA pointer. The fields used by the delete chain are listed below.

Field Format Used by Purpose
CA_REQUEST_ID CHAR(6) All three Selects the operation. LGDPVS01 uses its 4th character.
CA_RETURN_CODE PIC ‘99’ All three Status returned to the caller
CA_CUSTOMER_NUM PIC ‘9999999999’ All three Customer key
CA_POLICY_NUM PIC ‘9999999999’ All three Policy key
Common policy fields (CA_ISSUE_DATE, CA_EXPIRY_DATE, CA_BROKERID, CA_BROKERSREF, CA_PAYMENT) and the type-specific union Fixed-width None for the delete logic Passed through; only used as logged COMMAREA content

The COMMAREA buffer is COMM_AREA_RAW, a CHAR(32500) area. The request-specific section is a UNION of 32,482 bytes, and the policy-specific part of it is 32,400 bytes. The Endowment, House, Motor, Commercial and Claim layouts overlay each other there.

2.3 Return Code Summary

Code Set by Meaning
00 LGDPOL01, LGDPDB01 Success. LGDPVS01 leaves the incoming value unchanged on success.
81 LGDPVS01 VSAM KSDSPOLY delete failed (any response other than NORMAL)
90 LGDPDB01 Db2 delete returned a non-zero SQLCODE
98 LGDPOL01, LGDPDB01 COMMAREA shorter than the 28-byte header
99 LGDPOL01, LGDPDB01 Unrecognised request ID

3. End-to-End Processing Flow

3.1 Sequence of Operations (Successful Delete)

3.2 Failure Paths Across the Chain

An error in a downstream program travels back up the chain through the shared COMMAREA:

  • LGDPDB01 does not inspect CA_RETURN_CODE after linking to LGDPVS01, and it does not reset it. Any code set by LGDPVS01, such as 81, is therefore still in the COMMAREA when LGDPDB01 returns.
  • LGDPOL01 then tests CA_RETURN_CODE > 0 after its own link and returns immediately with that code.

4. LGDPOL01 – Policy Delete Dispatcher

4.1 Responsibilities

LGDPOL01 is the entry point (Proc(COMM_AREA_PTR) Options(Main)). It does the following:

  1. Saves EIBTRNID, EIBTRMID and EIBTASKN for diagnostics.
  2. Validates that a COMMAREA exists and is at least 28 bytes long (WS_CA_HEADER_LEN).
  3. Copies the customer and policy numbers into the error message record.
  4. Uppercases CA_REQUEST_ID, so the check is case-insensitive.
  5. Links to LGDPDB01 for the four valid request IDs.
  6. Returns the outcome in CA_RETURN_CODE.

LGDPOL01 also declares an 8-character constant for LGDPVS01, but it never uses it. The VSAM delete is always reached through LGDPDB01.

4.2 Dispatch Logic

PLI 
CA_REQUEST_ID = UPPERCASE(CA_REQUEST_ID);
SELECT (CA_REQUEST_ID);
  WHEN ('01DEND', '01DHOU', '01DCOM', '01DMOT')
    DO;
      CALL DELETE_POLICY_DB2_INFO;
      IF ( CA_RETURN_CODE > 0 ) THEN
        EXEC CICS RETURN;
    END;
  OTHERWISE
    CA_RETURN_CODE = '99';
END;
EXEC CICS RETURN;

All four request IDs follow the same delete path. The program does not check that the request ID matches the actual type of the policy. The policy type is resolved downstream through the foreign-key relationship.

4.3 Link to the Db2 Delete Program

PLI 
EXEC CICS LINK PROGRAM(LGDPDB01)
              COMMAREA(COMM_AREA)
              LENGTH(32500);

4.4 Behaviour by Input

Condition Result
EIBCALEN = 0 Writes NO COMMAREA RECEIVED to the log, then EXEC CICS ABEND ABCODE('LGCA') NODUMP
EIBCALEN < 28 CA_RETURN_CODE = '98', immediate return; nothing is logged
Request ID not recognised CA_RETURN_CODE = '99', no link; nothing is logged
Valid request ID Link to LGDPDB01; any non-zero returned code is passed straight back to the caller

5. LGDPDB01 – Db2 Policy Delete

5.1 Responsibilities

LGDPDB01 is a reentrant CICS/Db2 program (Options(Main,Reentrant)) that deletes one row from the POLICY table. It performs the following steps:

  1. Resets the Db2 host variables and saves the EIB identifiers.
  2. Repeats the COMMAREA presence and length checks (LGCA abend, or return code 98).
  3. Converts CA_CUSTOMER_NUM and CA_POLICY_NUM into the FIXED BIN(31) host variables DB2_CUSTOMERNUM_INT and DB2_POLICYNUM_INT.
  4. Saves both numbers in the error message record.
  5. Checks the request ID (01DEND, 01DHOU, 01DCOM or 01DMOT; any other value gives return code 99).
  6. Deletes the POLICY row.
  7. Links to LGDPVS01 only if the delete succeeded.

5.2 The Delete Statement

PLI 
EM_SQLREQ = ' DELETE POLICY  ';
EXEC SQL
  DELETE FROM POLICY
  WHERE CUSTOMERNUMBER = :DB2_CUSTOMERNUM_INT
    AND POLICYNUMBER   = :DB2_POLICYNUM_INT;

IF SQLCODE ¬= 0 THEN
  DO;
    CA_RETURN_CODE = '90';
    CALL WRITE_ERROR_MESSAGE;
    EXEC CICS RETURN;
  END;

The delete is keyed on both customer number and policy number. A policy can therefore be deleted only under the customer who owns it.

5.3 Cascade to Child Tables

LGDPDB01 deletes only from POLICY. The database foreign-key definitions remove the matching row in the type-specific table. The cascade must be defined in the database, because the program contains no code for it.

erDiagram POLICY { int POLICYNUMBER "delete criterion" int CUSTOMERNUMBER "delete criterion" string ISSUEDATE string EXPIRYDATE int BROKERID string BROKERSREFERENCE int PAYMENT } ENDOWMENT { int POLICYNUMBER "FK, cascade delete" int SUMASSURED string LIFEASSURED } HOUSE { int POLICYNUMBER "FK, cascade delete" string PROPERTYTYPE int VALUE } MOTOR { int POLICYNUMBER "FK, cascade delete" string REGNUMBER int PREMIUM } COMMERCIAL { int POLICYNUMBER "FK, cascade delete" string PROPTYPE } POLICY ||--o| ENDOWMENT : "has" POLICY ||--o| HOUSE : "has" POLICY ||--o| MOTOR : "has" POLICY ||--o| COMMERCIAL : "has"

A policy has at most one child row, in the table that matches its type. The request ID selects which type is being deleted, but the SQL itself is identical for all four.

5.4 SQLCODE 100 Behaviour (Code vs. Comment)

An in-code comment says that SQLCODE 100 (row not found) should be treated as success, because the end result is that the record no longer exists. The actual test is SQLCODE <> 0. A delete that finds no row therefore sets return code 90, writes an error message, and skips the VSAM delete. Plan callers and operations around the coded behaviour, not the comment.

5.5 Link to the VSAM Delete Program

PLI 
EXEC CICS LINK PROGRAM('LGDPVS01')
              COMMAREA(COMM_AREA)
              LENGTH(32500);

This link runs only after a successful Db2 delete. If the Db2 delete fails, the RETURN inside the error branch stops the chain, so the VSAM file is not touched. LGDPDB01 does not check anything after the link.

6. LGDPVS01 – VSAM Policy Delete

6.1 Responsibilities

LGDPVS01 is the last program in the chain. It deletes the policy record from the VSAM KSDS file KSDSPOLY. It does no validation. It builds a 21-byte composite key and issues the delete.

6.2 Key Construction

graph LR R[CA_REQUEST_ID
4th character] --> K C[CA_CUSTOMER_NUM
10 bytes] --> K P[CA_POLICY_NUM
10 bytes] --> K K[WF_POLICY_KEY
21 bytes] --> D[EXEC CICS DELETE
FILE KSDSPOLY]
Key part Source Length
WF_Request_ID SUBSTR(CA_Request_ID,4,1) 1
WF_Customer_Num CA_CUSTOMER_NUM 10
WF_Policy_Num CA_POLICY_NUM 10

Taking the 4th character of the request ID gives a one-letter policy type code:

Request ID Key prefix
01DEND E
01DHOU H
01DCOM C
01DMOT M

For example, motor policy 4567 of customer 123 is stored under the key M00000001230000004567. The VSAM record must have been stored with the same prefix for the delete to find it.

6.3 The Delete Command

PLI 
WS_Commarea_Len = EIBCALEN;
WF_Request_ID   = SUBSTR(CA_Request_ID, 4, 1);
WF_Policy_Num   = CA_POLICY_NUM;
WF_Customer_Num = CA_CUSTOMER_NUM;

EXEC CICS DELETE FILE('KSDSPOLY')
              RIDFLD(WF_Policy_Key)
              KEYLENGTH(21)
              RESP(WS_RESP);

IF WS_RESP = DFHRESP(NORMAL) THEN
  EXEC CICS RETURN;
ELSE
  DO;
    WS_RESP2       = EIBRESP2;
    CA_RETURN_CODE = '81';
    CALL WRITE_ERROR_MESSAGE;
    EXEC CICS RETURN;
  END;

Every non-NORMAL response (NOTFND, IOERR, a disabled file, and so on) is handled the same way: return code 81 and a log entry. The program does not distinguish the causes.

6.4 Limitations

  • There is no check of EIBCALEN before the key is built, so there is no 98 or LGCA handling in this program. It relies on LGDPOL01 and LGDPDB01 having validated the COMMAREA.
  • On success the return code is left unchanged. It is not reset to 00.
  • A missing record is reported as an error (81).

7. Error Logging

7.1 The WRITE_ERROR_MESSAGE Routine

LGDPOL01, LGDPDB01 and LGDPVS01 each contain a WRITE_ERROR_MESSAGE routine with the same structure. It does the following:

  1. Calls ASKTIME and FORMATTIME, which produce an MMDDYYYY date and a time.
  2. Fills the ERROR_MSG record and links to LGSTSQ to write it to the queue.
  3. If EIBCALEN > 0, copies up to 90 bytes of the COMMAREA into CA_DATA. It then links to LGSTSQ again with CA_ERROR_MSG, whose text starts with COMMAREA=.
PLI 
EXEC CICS ASKTIME ABSTIME(WS_ABSTIME);
EXEC CICS FORMATTIME ABSTIME(WS_ABSTIME)
                     MMDDYYYY(WS_DATE)
                     TIME(WS_TIME);
EM_DATE = WS_DATE;
EM_TIME = WS_TIME;

EXEC CICS LINK PROGRAM('LGSTSQ')
              COMMAREA(ERROR_MSG)
              LENGTH(STG(ERROR_MSG));

IF EIBCALEN > 0 THEN
  DO;
    IF EIBCALEN < 91 THEN
      CA_DATA = LEFT(COMM_AREA_RAW, EIBCALEN);
    ELSE
      CA_DATA = LEFT(COMM_AREA_RAW, 90);
    EXEC CICS LINK PROGRAM('LGSTSQ')
                  COMMAREA(CA_ERROR_MSG)
                  LENGTH(STG(ERROR_MSG));
  END;

L->>Q: Write COMMAREA record end

7.3 What Each Program Logs

Program Logged when Message contents
LGDPOL01 No COMMAREA only (EIBCALEN = 0) Date, time, LGDPOL01, text NO COMMAREA RECEIVED. The COMMAREA dump is not written, because its length is 0.
LGDPDB01 No COMMAREA, or Db2 delete failure (SQLCODE <> 0) Date, time, LGDPDB01, customer number, policy number, DELETE POLICY and the SQLCODE (EM_SQLRC), followed by up to 90 bytes of COMMAREA
LGDPVS01 VSAM delete failure Date, time, LGDPVS01, customer number, Delete file KSDSPOLY, RESP and RESP2, followed by up to 90 bytes of COMMAREA. The policy number field is never filled and stays blank.

The return codes 98 and 99 are not logged by any program.

7.4 Known Logging Quirks

  • Both LINK calls to LGSTSQ use LENGTH(STG(ERROR_MSG)), including the one that passes CA_ERROR_MSG. The length is therefore not the length of the structure actually passed.
  • No RESP checks are made on the LGSTSQ links or on ASKTIME and FORMATTIME.
  • EM_MSG_TEXT (CHAR(63)) shares storage with the customer, policy and SQL detail fields through a UNION, so a free-text message and the structured detail cannot both appear in one record.

8. Worked Examples

8.1 Successful Motor Policy Delete

Input (COMMAREA, EIBCALEN = 32500)

Field Value
CA_REQUEST_ID 01DMOT
CA_CUSTOMER_NUM 0000000123
CA_POLICY_NUM 0000004567

Flow

  1. LGDPOL01 validates the COMMAREA and links to LGDPDB01.
  2. LGDPDB01 deletes the POLICY row, and the cascade removes the MOTOR row (SQLCODE 0). It then links to LGDPVS01.
  3. LGDPVS01 deletes the VSAM record with key M00000001230000004567.
  4. The chain returns with CA_RETURN_CODE = '00'.

8.2 Lowercase Request ID

CA_REQUEST_ID = 01dhou is converted by UPPERCASE to 01DHOU in LGDPOL01. It then follows the normal house-policy path, and the caller sees 01DHOU in the returned COMMAREA.

8.3 Unrecognised Request ID

CA_REQUEST_ID = 01INQC matches none of the four delete IDs. LGDPOL01 sets CA_RETURN_CODE = '99' and returns. LGDPDB01 and LGDPVS01 are never called, and no data changes.

8.4 COMMAREA Too Short

With EIBCALEN = 20, which is less than 28, LGDPOL01 sets CA_RETURN_CODE = '98' and returns immediately. The customer and policy numbers are not read, no delete is attempted, and nothing is logged.

8.5 No COMMAREA

With EIBCALEN = 0, LGDPOL01 sets NO COMMAREA RECEIVED, links to LGSTSQ to log it, and abends with LGCA (NODUMP). No return code is returned.

8.6 Db2 Failure

LGDPDB01 receives SQLCODE -911 for a motor delete.

  1. LGDPDB01 sets CA_RETURN_CODE = '90' and logs the date, time, customer, policy, DELETE POLICY and the SQLCODE.
  2. It returns without linking to LGDPVS01, so the VSAM file is untouched.
  3. LGDPOL01 sees a non-zero return code and returns it to the caller.

8.7 VSAM Record Not Found

The Db2 delete succeeds, but the KSDSPOLY record is not found (RESP is not NORMAL).

  1. LGDPVS01 sets CA_RETURN_CODE = '81' and writes two log records through LGSTSQ: the error message with RESP and RESP2, then the COMMAREA content.
  2. The Db2 row is already deleted at this point. Nothing in the chain undoes it.
  3. The 81 code propagates back through LGDPDB01 to LGDPOL01 and then to the caller.

9. Design Notes and Constraints

Topic Behaviour
Deletion order Db2 first, then VSAM. A Db2 failure prevents the VSAM step.
Atomicity The two stores are not coordinated by the code. A VSAM failure after a successful Db2 delete leaves the Db2 side deleted and returns 81.
Cascade Child-table removal relies entirely on database foreign-key definitions, not on program code.
Validation The request ID is validated in LGDPOL01 and LGDPDB01. Numeric content, policy ownership and the other policy fields are not validated by LGDPOL01.
Minimum length Only the 28-byte common header is checked. No type-specific minimum is enforced, and the code comment notes that the Endowment VARCHAR is not allowed for.
Return code on success LGDPOL01 and LGDPDB01 set 00. LGDPVS01 leaves the incoming value unchanged.
RESP handling No RESP/RESP2 checks on CICS commands, except on the KSDSPOLY delete. No PL/I ON units or HANDLE CONDITION.
Unused items LGDPOL01 declares LGDPVS01 but does not use it. LGDPDB01 declares an unused LGDPVS1 literal.
Environment All three programs must run under CICS. LGDPDB01 also needs the CICS-Db2 attachment. The KSDSPOLY file, LGSTSQ and the child-table foreign keys must be defined.
