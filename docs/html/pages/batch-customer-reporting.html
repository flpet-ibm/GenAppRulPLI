Batch Customer Reporting

This page describes the non-CICS batch programs that produce customer detail lines from the Db2 CUSTOMER table. LGBATCH drives the report from an input file of customer numbers. LGBATCHF formats each report line. LGBATDB2 is a single-customer test driver for the same logic.

1. Overview

1.1 Purpose

The batch customer reporting application produces a customer detail report outside the online (CICS) environment. All three programs are Enterprise PL/I Options(Main) or called-subroutine modules. They share one commarea layout (LGCMAREA) and one Db2 table (CUSTOMER).

Program Role Inputs Outputs
LGBATCH Batch driver. Reads customer numbers, looks up each customer in Db2, calls the formatter, and writes the report. CUSTIN file (10-byte records), Db2 CUSTOMER CUSTRPT file (80-byte records), return code 16 if CUSTIN can’t be opened
LGBATCHF Formatting subroutine. Builds one 80-character report line. Customer number, commarea pointer LS_LINE (80 characters), a DISPLAY trace
LGBATDB2 Test driver. Looks up customer number 1 and displays the formatted line. Hard-coded key 1, Db2 CUSTOMER Console/SYSOUT messages

1.2 Key Characteristics

  • The report contains one line for every input record. There is no filtering, de-duplication or skipping.
  • Each line has the form Customer <10-digit number> is <first name> <last name>.
  • A customer that isn’t found, or whose SELECT fails, is still reported. The line is built from whatever the commarea still holds from the previous record.
  • LGBATCHF is loaded dynamically with FETCH by both LGBATCH and LGBATDB2.
  • Db2 access uses a singleton SELECT ... INTO host-variable pattern against the commarea fields.

2. System Architecture

2.1 Component Architecture

LGBATCH and LGBATDB2 are two alternative entry points. Both use the same Db2 lookup pattern, the same commarea storage (BATCH_COMM_AREA) and the same formatter (LGBATCHF).

2.2 Shared Communication Area

All three programs include the LGCMAREA layout (plinc/LGCMAREA.inc).

  • BATCH_COMM_AREA is a CHAR(32500) work area in the drivers.
  • COMM_AREA_PTR is set to ADDR(BATCH_COMM_AREA).
  • A BASED COMM_AREA union overlays that storage, so the Db2 SELECT loads data straight into the CA_* fields.
  • LGBATCHF receives the pointer and overlays the same layout on the caller’s storage.

Only the customer request portion is used in this application.

2.3 Runtime Environment

  • Enterprise PL/I for z/OS with the Language Environment runtime. It supports FETCH, record I/O, ON conditions, DISPLAY, STOP and PLIRETC.
  • A Db2 precompile or coprocessor step, plus a bound plan or package (GenAppBind.jcl).
  • The CUSTOMER table, defined by GenAppDDL.jcl.
  • The LGBATCHF load module in the load library or STEPLIB.
  • Run JCL with CUSTIN and CUSTRPT DD statements, for LGBATCH only.

4. LGBATCH: Batch Report Driver

4.1 Initialization and Resource Setup

On start-up the program does the following, in order:

  1. Sets COMM_AREA_PTR to the address of BATCH_COMM_AREA.
  2. Executes FETCH LGBATCHF to load the formatter.
  3. Establishes ON UNDEFINEDFILE(CUSTIN). This handler displays 'FILE STATUS AT OPEN CUSTIN', calls PLIRETC(16) and issues STOP.
  4. Opens CUSTIN (RECORD INPUT SEQUENTIAL ENV(FB RECSIZE(10))) and CUSTRPT (RECORD OUTPUT SEQUENTIAL ENV(FB RECSIZE(80))).
  5. Establishes ON ENDFILE(CUSTIN), which sets FI_EOF = '1'B.

4.2 Main Processing Loop

The program performs a priming read, then loops until FI_EOF is set. Each iteration calls PROCESS_RECORD and then reads the next record. An empty input file skips the loop and ends normally.

flowchart TD S([Start]) --> P[Set COMM_AREA_PTR, FETCH LGBATCHF] P --> O{CUSTIN opens?} O -- No --> E[DISPLAY message
PLIRETC 16, STOP] O -- Yes --> R1[Open CUSTRPT
Priming READ CUSTIN] R1 --> L{FI_EOF?} L -- No --> PR[PROCESS_RECORD] PR --> R2[READ next CUSTIN record] R2 --> L L -- Yes --> C[CLOSE CUSTIN and CUSTRPT] C --> X([RETURN])

4.3 PROCESS_RECORD

For each customer, PROCESS_RECORD does the following in a fixed order:

  1. Converts CUSTIN_CUSTNUMBER into the binary host variable DB2_CUSTOMERNUMBER_INT (FIXED BIN(31)).
  2. Calls GET_CUSTOMER_INFO to run the SELECT.
  3. Calls LGBATCHF(CUSTIN_CUSTNUMBER, COMM_AREA_PTR, CUSTRPT_LINE).
  4. Executes WRITE FILE(CUSTRPT) FROM(CUSTRPT_LINE).

4.4 GET_CUSTOMER_INFO and Return Codes

The procedure sets EM_SQLREQ to ' SELECT CUSTOMER'. It then runs a singleton SELECT of nine columns into the commarea fields and maps SQLCODE to a business return code.

SQLCODE CA_RETURN_CODE Meaning Extra action
0 00 Success None
100 01 Customer not found None; the line is still formatted
Other 90 Database error Calls WRITE_ERROR_MESSAGE
stateDiagram-v2 [*] --> Select Select --> Found: SQLCODE 0 Select --> NotFound: SQLCODE 100 Select --> DbError: other SQLCODE Found --> Format: CA_RETURN_CODE = 00 NotFound --> Format: CA_RETURN_CODE = 01 DbError --> BuildMsg: CA_RETURN_CODE = 90 BuildMsg --> Format: ERROR_MSG built, not written Format --> [*]: LGBATCHF + WRITE

4.5 WRITE_ERROR_MESSAGE

This routine fills the in-memory ERROR_MSG structure:

  • SQLCODE goes to EM_SQLRC.
  • WS_DATE goes to EM_DATE.
  • WS_TIME goes to EM_TIME.

The message is never displayed or written. WS_DATE and WS_TIME stay blank, and EM_CUSNUM and EM_POLNUM are never populated. Only CA_RETURN_CODE = '90' shows that an error occurred, and that code isn’t written anywhere either.

4.6 Termination

After the loop ends, the program closes CUSTIN and CUSTRPT and executes RETURN. Normal completion sets no non-zero return code, even if some records hit the not-found or error paths.

5. LGBATCHF: Report Line Formatter

LGBATCHF is a leaf subroutine with no file, database or CICS access. The source documentation also refers to it as LGBATCF in places. It takes three parameters by reference:

Parameter Type Direction Description
CUSTNUMBER PIC '9999999999' In Customer number, printed with leading zeros
COMM_PTR PTR In Pointer to the caller’s LGCMAREA commarea
LS_LINE CHAR(80) Out Formatted report line

5.1 Processing Logic

The routine assigns COMM_AREA_PTR = COMM_PTR, so the based structure overlays the caller’s storage. It then emulates COBOL STRING ... DELIMITED BY SPACE for each name using INDEX:

  • If no blank is found (position 0), the token is the whole field.
  • If the blank is in position 1, the token is an empty string.
  • Otherwise, the token is the text before the first blank.

It then builds the line, displays a trace message and returns.

graph TD A([Entry]) --> B[COMM_AREA_PTR = COMM_PTR] B --> C[INDEX CA_FIRST_NAME for blank] C --> D[Derive FIRST_TOKEN] D --> E[INDEX CA_LAST_NAME for blank] E --> F[Derive LAST_TOKEN] F --> G["LS_LINE = 'Customer ' + CUSTNUMBER + ' is ' + FIRST_TOKEN + ' ' + LAST_TOKEN"] G --> H["DISPLAY 'LGBATCHF WAS HERE... ' + LS_LINE"] H --> I([RETURN])

5.2 Formatting Rules

  • The fixed text takes 24 characters (9 + 10 + 4 + 1). The tokens can add at most 10 + 20 characters, so the line never exceeds 80 characters.
  • Work variables are FIRST_TOKEN CHAR(10) VAR, LAST_TOKEN CHAR(20) VAR and POS FIXED BIN(15).
  • "Mary Ann" becomes Mary, and "Van Der Berg" becomes Van.
  • An empty first name leaves two consecutive blanks. An empty last name leaves a trailing blank.
  • The routine does no validation, has no error path, does not check for a null pointer, and never sets CA_RETURN_CODE.
  • The trace DISPLAY runs on every call and cannot be switched off. For LGBATCH this means one trace line per customer in the job output.

6. LGBATDB2: Single-Customer Test Driver

LGBATDB2 is a batch main procedure that takes no parameters and reads no files. It gives a quick end-to-end check of the Db2 retrieval and LGBATCHF formatting.

  1. Sets COMM_AREA_PTR to ADDR(BATCH_COMM_AREA).
  2. Fetches LGBATCHF.
  3. Displays SQLCODE and SQLSTATE. This happens before any SQL runs, so it only shows initial SQLCA values.
  4. Sets DB2_CUSTOMERNUMBER_INT = 1.
  5. Calls PROCESS_RECORD, which does the following:
    • Calls GET_CUSTOMER_INFO.
    • Moves the key into CUSTIN_CUSTNUMBER.
    • Calls LGBATCHF.
    • Displays CUSTRPT_LINE.
  6. Returns.

Unlike LGBATCH, it doesn’t check SQLCODE after the SELECT, doesn’t set CA_RETURN_CODE and has no ON units. Changing the customer means changing the constant in source.

8.2 LGBATCHF Call Interface

The entry declaration is the same in both drivers:

PLI 
ENTRY(PIC '9999999999', PTR, CHAR(80))

The call, as made from PROCESS_RECORD in both drivers, is:

PLI 
CALL LGBATCHF(CUSTIN_CUSTNUMBER, COMM_AREA_PTR, CUSTRPT_LINE);

8.3 Db2 Access Pattern

The singleton SELECT used by GET_CUSTOMER_INFO retrieves the following columns into the commarea host variables:

SQL 
SELECT FIRSTNAME, LASTNAME, DATEOFBIRTH, HOUSENAME, HOUSENUMBER,
       POSTCODE, PHONEMOBILE, PHONEHOME, EMAILADDRESS
  INTO :CA_FIRST_NAME, :CA_LAST_NAME, :CA_DOB, :CA_HOUSE_NAME,
       :CA_HOUSE_NUM, :CA_POSTCODE, :CA_PHONE_MOBILE,
       :CA_PHONE_HOME, :CA_EMAIL_ADDRESS
  FROM CUSTOMER
 WHERE CUSTOMERNUMBER = :DB2_CUSTOMERNUMBER_INT

8.4 SQLCODE Mapping and Open-Failure Handling (LGBATCH)

This is a sketch of the logic described for LGBATCH, not verbatim source:

PLI 
SELECT (SQLCODE);
  WHEN (0)   CA_RETURN_CODE = '00';
  WHEN (100) CA_RETURN_CODE = '01';
  OTHERWISE  DO;
               CA_RETURN_CODE = '90';
               CALL WRITE_ERROR_MESSAGE;
             END;
END;
PLI 
ON UNDEFINEDFILE(CUSTIN) BEGIN;
   DISPLAY('FILE STATUS AT OPEN CUSTIN');
   CALL PLIRETC(16);
   STOP;
END;
ON ENDFILE(CUSTIN) FI_EOF = '1'B;

8.5 Report Line Construction (LGBATCHF)

PLI 
LS_LINE = 'Customer ' || CUSTNUMBER || ' is ' || FIRST_TOKEN || ' ' || LAST_TOKEN;
DISPLAY('LGBATCHF WAS HERE... ' || LS_LINE);

10.1 Known Limitations

  • Stale data: a not-found or failed lookup produces a line from the previous customer’s commarea contents. CA_RETURN_CODE is the only indicator, and LGBATCHF doesn’t read it.
  • Silent SQL errors: LGBATCH builds ERROR_MSG but never writes it. LGBATDB2 ignores SQL results entirely.
  • Nullable columns: no indicator variables are declared. A NULL column gives SQLCODE -305, which LGBATCH maps to '90' and LGBATDB2 ignores.
  • Truncation: values longer than the host-variable lengths are truncated. For example, the email address is limited to 100 characters.
  • Name truncation: names are cut at the first embedded blank by LGBATCHF.
  • Return code: the job return code stays 0 on normal completion, even if records hit the not-found or error paths.
  • Unused commarea fields: CA_CUSTOMER_NUM and CA_NUM_POLICIES are never set by the drivers.

11. Dependencies and Constraints Summary

  • Input format: CUSTIN must be fixed-blocked with 10-byte records. Each record holds a 10-digit customer number, and the programs don’t validate it.
  • Single-row lookup: the SELECT is keyed on CUSTOMERNUMBER. A multi-row result gives SQLCODE -811.
  • Interface: LGBATCHF must receive a 10-digit picture, a pointer and an CHAR(80) buffer, in that order.
  • Order of operations: the pointer must be set and LGBATCHF fetched before use. Files must be opened before the first read. The SELECT must complete before the formatter is called.
  • Sizing: the commarea work area is 32,500 bytes, and the report line is 80 bytes. There is no limit on the number of input records.
  • Environment: the programs are batch only and must not run under CICS. They need a Db2 attachment such as DSN or IKJEFT01, the LGBATCHF load module, and the CUSTOMER table.
