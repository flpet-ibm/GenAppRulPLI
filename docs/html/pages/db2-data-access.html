Db2 Data Access Programs

1. Overview

The Db2 data access programs are the back-end tier of the GenApp general insurance application, written in Enterprise PL/I for CICS. Each one is a CICS Options(Main) program that an orchestrator reaches with EXEC CICS LINK. It receives a shared COMMAREA (COMM_AREA, based on COMM_AREA_PTR, 32,500 bytes). It runs embedded SQL against the Db2 tables, reports the outcome in CA_RETURN_CODE, and often links on to a VSAM-side twin to keep the file store in step.

The programs cover these tables:

  • Customer data: CUSTOMER and CUSTOMER_SECURE.
  • Policy data: POLICY.
  • Policy-type tables: ENDOWMENT, HOUSE, MOTOR, COMMERCIAL and CLAIM.
Program Function Tables touched Linked programs
LGICDB01 Inquire customer CUSTOMER (SELECT) LGSTSQ
LGACDB01 Add customer CUSTOMER (INSERT) LGACVS01, LGACDB02, LGSTSQ
LGACDB02 Add customer security CUSTOMER_SECURE (INSERT) LGSTSQ
LGUCDB01 Update customer CUSTOMER (UPDATE) LGUCVS01, LGSTSQ
LGACUS01 Customer and policy service (add customer, offer, transfer, delete policy) CUSTOMER, POLICY LGACVS01, LGACDB02, LGSTSQ
LGAPDB01 Add policy or claim POLICY plus the type table LGAPVS01, LGSTSQ
LGIPDB01 Inquire policy or claim POLICY joined with the type tables LGSTSQ
LGUPDB01 Update policy POLICY, ENDOWMENT, HOUSE, MOTOR LGUPVS01, LGSTSQ
LGDPDB01 Delete policy POLICY (cascade to the type tables) LGDPVS01, LGSTSQ

2. System Architecture

The orchestrators (for example LGICUS01, LGIPOL01, LGUPOL01, LGDPOL01) pass a COMMAREA to a Db2 program. The Db2 program talks to Db2 through the CICS-Db2 attachment. It links to a VSAM program for the file-based copy of the data. It links to LGSTSQ whenever a diagnostic must be logged.

The architecture follows a few rules:

  • Db2 first, VSAM second. Add, update and delete programs complete the relational change before they link to the VSAM twin.
  • One logging path. Every program has its own WRITE_ERROR_MESSAGE procedure that links to the shared LGSTSQ.
  • No COMMIT or ROLLBACK in most programs. The unit of work is the CICS task. Two programs force a backout explicitly (see sections 7.1 and 7.3).

3. The Common Program Skeleton

All nine programs share the same structure.

3.1 COMMAREA Contract

Field Role
CA_REQUEST_ID CHAR(6) request code that selects the operation
CA_RETURN_CODE PIC '99' outcome returned to the caller
CA_CUSTOMER_NUM 10-digit customer key, converted to a FIXED BIN(31) host variable
CA_POLICY_NUM 10-digit policy key, converted to a FIXED BIN(31) host variable
request area A 32,482-byte UNION overlaying the customer, customer-security, policy and policy-type layouts

The COMMAREA layout comes from LGCMAREA and the policy host structures from LGPOLICY. Both are expanded inline in the sources.

3.2 Entry Validation Sequence

Each program runs these steps in the same order, so no SQL is issued with bad input.

graph TD A([Entry: COMM_AREA_PTR]) --> B[Copy EIBTRNID, EIBTRMID, EIBTASKN
into WS_HEADER, zero host variables] B --> C{EIBCALEN = 0} C -- Yes --> D[Set NO COMMAREA RECEIVED
WRITE_ERROR_MESSAGE] D --> E([ABEND LGCA NODUMP]) C -- No --> F[CA_RETURN_CODE = 00
save length and address] F --> G{EIBCALEN below minimum} G -- Yes --> H[CA_RETURN_CODE = 98
EXEC CICS RETURN] G -- No --> I[Convert keys to Db2 integers
save in ERROR_MSG] I --> J[Request-specific SQL]

The minimum COMMAREA length differs by program:

Program Minimum length
LGICDB01, LGACDB01, LGACUS01 90 bytes (18 header + 72 customer)
LGDPDB01, LGAPDB01 28-byte header, plus the type’s full length for LGAPDB01
LGIPDB01 Checked after the SELECT, from a 33-byte header/trailer plus the type’s full length
LGUCDB01, LGUPDB01, LGACDB02 Only the zero-length check

Typical code for the first check:

PLI 
IF (EIBCALEN = 0) THEN DO;
   EM_MSG_TEXT = ' NO COMMAREA RECEIVED';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS ABEND ABCODE('LGCA') NODUMP;
END;
CA_RETURN_CODE = '00';

3.3 Error Logging Through LGSTSQ

Each program’s WRITE_ERROR_MESSAGE writes two records through LGSTSQ. The first is the ERROR_MSG structure. The second is CA_ERROR_MSG, which is 'COMMAREA=' followed by at most 90 bytes of the COMMAREA. The second record is written only when EIBCALEN > 0.

sequenceDiagram participant P as Db2 program participant C as CICS participant Q as LGSTSQ P->>P: SQLCODE to EM_SQLRC P->>C: ASKTIME ABSTIME P->>C: FORMATTIME MMDDYYYY, TIME P->>Q: LINK with ERROR_MSG Note over Q: date, time, program, CNUM, PNUM, SQL request, SQLCODE alt EIBCALEN greater than 0 P->>P: CA_DATA = LEFT of COMM_AREA_RAW, up to 90 bytes P->>Q: LINK with CA_ERROR_MSG end
PLI 
EM_SQLRC = SQLCODE;
EXEC CICS ASKTIME ABSTIME(WS_ABSTIME);
EXEC CICS FORMATTIME ABSTIME(WS_ABSTIME)
     MMDDYYYY(WS_DATE) TIME(WS_TIME);
EXEC CICS LINK PROGRAM('LGSTSQ')
     COMMAREA(ERROR_MSG) LENGTH(STG(ERROR_MSG));

Before each SQL statement, the program sets EM_SQLREQ to a short label such as ' SELECT CUSTOMER', ' INSERT POLICY' or ' UPDATE CUST '. The log then shows which statement failed. None of the LINK calls to LGSTSQ check RESP.

4. Customer Programs

4.1 LGICDB01: Customer Inquiry

LGICDB01 does a single-row SELECT from CUSTOMER. The key is CUSTOMERNUMBER, converted from CA_CUSTOMER_NUM into DB2_CUSTOMERNUMBER_INT. It returns nine columns straight into the COMMAREA: name, date of birth, house name and number, postcode, both phone numbers, and email. The columns are read without indicator variables, so a NULL in any of them would produce SQLCODE -305 and return code 90.

PLI 
SELECT (SQLCODE);
   WHEN (0)         CA_RETURN_CODE = '00';
   WHEN (100, -913) CA_RETURN_CODE = '01';
   OTHERWISE DO;
      CA_RETURN_CODE = '90';
      CALL WRITE_ERROR_MESSAGE;
      EXEC CICS RETURN;
   END;
END;

SQLCODE 100 and -913 both map to 01. 01 means customer not found or resource unavailable, and the caller cannot tell the two apart. Neither case is logged.

4.2 LGACDB01: Add Customer

LGACDB01 allocates a customer number and inserts the row. It prefers the CICS named counter GENACUSTNUM in pool GENA. If the counter call does not return NORMAL, it sets LGAC_NCS to 'NO' and lets Db2 generate the key from an identity column.

graph TD A[GET COUNTER GENACUSTNUM, POOL GENA] --> B{RESP NORMAL} B -- Yes --> C[DB2_CUSTOMERNUM_INT = counter value
LGAC_NCS = ON] B -- No --> D[LGAC_NCS = NO
DB2_CUSTOMERNUM_INT = 0] C --> E[INSERT with explicit CUSTOMERNUMBER] D --> F[INSERT with DEFAULT CUSTOMERNUMBER] F --> G[SET host var = IDENTITY_VAL_LOCAL] E --> H{SQLCODE = 0} G --> H H -- No --> I[CA_RETURN_CODE = 90
WRITE_ERROR_MESSAGE, RETURN] H -- Yes --> J[CA_CUSTOMER_NUM = new number] J --> K[LINK LGACVS01 length 225] K --> L[Build CDB2AREA
LINK LGACDB02 length 32500] L --> M([RETURN])

The named-counter fallback is silent. It sets no return code and writes no log message.

PLI 
EXEC CICS GET COUNTER(GENACOUNT) POOL(GENAPOOL)
     VALUE(LASTCUSTNUM) RESP(WS_RESP);
IF WS_RESP ^= DFHRESP(NORMAL) THEN DO;
   LGAC_NCS = 'NO';
   DB2_CUSTOMERNUM_INT = 0;
END;
ELSE DB2_CUSTOMERNUM_INT = LASTCUSTNUM;

After the insert, LGACDB01 fills the security commarea CDB2AREA with hard-coded values and links to LGACDB02:

CDB2AREA field Value
D2_REQUEST_ID 02ACUS
D2_CUSTOMER_NUM The new customer number
D2_CUSTSECR_PASS 5732fec825535eeafb8fac50fee3a8aa (fixed hash)
D2_CUSTSECR_COUNT 0000
D2_CUSTSECR_STATE N (new)

The code checks CA_RETURN_CODE after the LGACDB02 link, but LGACDB02 writes its code to its own CDB2AREA and not to COMM_AREA. The check therefore sees a value LGACDB01 set earlier.

4.3 LGACDB02: Add Customer Security

LGACDB02 accepts only CA_REQUEST_ID = '02ACUS'. It copies CA_CUSTOMER_NUM and the 4-character CA_CUSTSECR_COUNT into integer host variables, then inserts one row into CUSTOMER_SECURE.

PLI 
EM_SQLREQ = ' INSERT SECURITY';
EXEC SQL INSERT INTO CUSTOMER_SECURE
         (customerNumber, customerPass, state_indicator, pass_changes)
  VALUES (:DB2_CUSTOMERNUM_INT, :CA_CUSTSECR_PASS,
          :CA_CUSTSECR_STATE, :DB2_CUSTOMERCNT_INT);
IF SQLCODE ^= 0 THEN DO;
   CA_RETURN_CODE = '98';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS RETURN;
END;
Return code Meaning
00 Row inserted
98 Insert failed (any non-zero SQLCODE, for example a duplicate key)
99 Request ID is not 02ACUS (no SQL is issued)

Here 98 means a Db2 failure. In other programs 98 means the COMMAREA is too short. The defaults WS_CS_PASSWORD, WS_CS_STATE and WS_CA_COUNT are declared but not used.

4.4 LGUCDB01: Update Customer

LGUCDB01 updates all nine customer columns for one CUSTOMERNUMBER. Fields are not skipped when blank.

PLI 
EM_SQLREQ = ' UPDATE CUST    ';
EXEC SQL UPDATE CUSTOMER
   SET FIRSTNAME = :CA_FIRST_NAME,  LASTNAME = :CA_LAST_NAME,
       DATEOFBIRTH = :CA_DOB,       HOUSENAME = :CA_HOUSE_NAME,
       HOUSENUMBER = :CA_HOUSE_NUM, POSTCODE = :CA_POSTCODE,
       PHONEMOBILE = :CA_PHONE_MOBILE, PHONEHOME = :CA_PHONE_HOME,
       EMAILADDRESS = :CA_EMAIL_ADDRESS
 WHERE CUSTOMERNUMBER = :DB2_CUSTOMERNUM_INT;

SQLCODE 100 gives return code 01 with no log entry. Any other non-zero SQLCODE gives 90 and logs the error. The program always links to LGUCVS01 with 225 bytes, even after a 01 or 90. The caller must check CA_RETURN_CODE.

4.5 LGACUS01: Customer and Policy Service

LGACUS01 contains four operations selected by ACTION_CODE:

ACTION_CODE Operation CA_REQUEST_ID set
1 ONBOARD_CUSTOMER 01ICUS
2 OFFER_CUSTOMER 02OCUS
3 TRANSFER_CUSTOMER 02UCUS
4 DELETE_CUSTOMER 02DCUS

ACTION_CODE is initialised to '0' and never changed. The OTHERWISE branch is therefore always taken. As coded, the program validates the COMMAREA and returns, and none of the four operations runs. It is a design artefact carried over from the COBOL original.

If the operations were reachable, they would work as follows:

  • Onboard. Same logic as LGACDB01: named counter or identity, INSERT INTO CUSTOMER, LINK LGACVS01, LINK LGACDB02.
  • Offer and transfer. Both insert a POLICY row. POLICYNUMBER is DEFAULT, LASTCHANGED is CURRENT TIMESTAMP, and the identity value is read back with IDENTITY_VAL_LOCAL().
  • Delete. DELETE FROM POLICY WHERE CUSTOMERNUMBER = … AND POLICYNUMBER = …. Cascade rules remove the type-table rows. Any non-zero SQLCODE, including 100, gives 90, even though a comment says 100 is acceptable.

5. Policy Programs

5.1 LGAPDB01: Add Policy or Claim

LGAPDB01 validates the request code, then inserts into POLICY and the matching type table.

CA_REQUEST_ID Type DB2_POLICYTYPE Required COMMAREA length
01AEND Endowment E 28 + 124
01AHOU House H 28 + 130
01AMOT Motor M 28 + 137
01ACOM Commercial C 28 only
01ACLM Claim X 28 only

Anything else returns 99. A claim does not create a POLICY row. It is attached to an existing policy through CA_POLICY_NUM.

sequenceDiagram participant Caller participant D as LGAPDB01 participant DB as Db2 participant V as LGAPVS01 Caller->>D: LINK with COMMAREA D->>D: Validate length and request ID alt Not a claim D->>DB: SELECT COUNT of active M/H policies (bundling) D->>DB: SELECT COUNT of active broker policies (commission) D->>DB: INSERT INTO POLICY (DEFAULT policy number) D->>DB: SET host var = IDENTITY_VAL_LOCAL D->>DB: SELECT LASTCHANGED end D->>DB: INSERT into type table alt SQL error after POLICY insert D->>D: Return code 90, log, ABEND LGSQ else success D->>V: LINK 32500 bytes D-->>Caller: RETURN end

Pricing rules inside INSERT_POLICY and the type-specific procedures:

  • House loading. Applies only to 01AHOU with a postcode strictly between 600000 and 699999. The payment rises by 20% for a value over 10,000,000 and under 15,000,000, by 40% for a value over 15,000,000 and under 20,000,000, and by 50% above 20,000,000.
  • Bundling discount. If the customer has more than two active M or H policies, the payment is reduced by 15%.
  • Broker commission. The commission is 0 to 5% of the adjusted payment, based on the broker’s active policy count: 0, 1, 2, 3, 4, or 5 and over.
  • Motor premium. The premium is multiplied by 1.0 for up to 2 accidents, 1.2 for 3 to 5, 1.5 for 6 to 8, and 3.0 above 8.
  • Commercial perils. VALIDATE_PREV_PERIL sums FLOODPERIL and WEATHERPERIL for the same ZIPCODE. A sum above 3 raises that premium by 15%.
  • Claims. UPDATE_BROKER_COMM counts the policy’s claims in the current year. If the count is above 3, it runs UPDATE POLICY SET COMMISSION = (COMMISSION / 2). The count is taken before the new claim is inserted.

The POLICY insert has its own SQLCODE handling:

PLI 
SELECT (SQLCODE);
   WHEN (0)    CA_RETURN_CODE = '00';
   WHEN (-530) DO;                 /* foreign key violation */
      CA_RETURN_CODE = '70';
      CALL WRITE_ERROR_MESSAGE;
      EXEC CICS RETURN;
   END;
   OTHERWISE DO;
      CA_RETURN_CODE = '90';
      CALL WRITE_ERROR_MESSAGE;
      EXEC CICS RETURN;
   END;
END;

Every later SQL failure (discount, commission, type insert, peril, claim count) sets 90, logs the error and then abends so Db2 backs out the POLICY row:

PLI 
CA_RETURN_CODE = '90';
CALL WRITE_ERROR_MESSAGE;
EXEC CICS ABEND ABCODE('LGSQ') NODUMP;

For endowments, WS_VARY_LEN = EIBCALEN - WS_REQUIRED_CA_LEN. If it is above 0, the insert includes the PADDINGDATA VARCHAR column. Otherwise that column is left out.

5.2 LGIPDB01: Inquire Policy or Claim

LGIPDB01 first tries EXEC CICS GET CONTAINER('ICOM-Data') on channel ICOM. If the container is found, the request ID and customer number come from it. Otherwise it falls back to the classic COMMAREA. It converts CA_REQUEST_ID to upper case and dispatches:

Request Routine Access method
01IEND GET_ENDOW_DB2_INFO Singleton SELECT, POLICY joined with ENDOWMENT
01IHOU GET_HOUSE_DB2_INFO Singleton SELECT, POLICY joined with HOUSE
01IMOT GET_MOTOR_DB2_INFO Singleton SELECT, POLICY joined with MOTOR
01ICOM GET_Commercial_DB2_INFO_1 Singleton SELECT by customer and policy
02ICOM GET_Commercial_DB2_INFO_2 Singleton SELECT by policy only; also returns the customer number
03ICOM GET_Commercial_DB2_INFO_3 Cust_Cursor, all commercial policies for a customer
05ICOM GET_Commercial_DB2_INFO_5 Zip_Cursor, commercial policies for a postcode
01ICLM GET_Claim_DB2_INFO_1 Singleton SELECT by claim number
02ICLM GET_Claim_DB2_INFO_2 CusClaim_Cursor, all claims for a customer
other none Return code 99

The singleton routines follow one pattern:

  1. Run the SELECT into working-storage host variables. The VARCHAR length of the endowment padding is not known in advance, so output does not go straight into the COMMAREA.
  2. On SQLCODE 0, compute the required length (WS_CA_HEADERTRAILER_LEN of 33 plus the type’s full length). If EIBCALEN is smaller, set 98 and return.
  3. Convert the integers to numeric pictures. Broker ID and payment are moved only when their indicator is not -1.
  4. Copy the common policy fields and the type block, then write the end-of-data marker FINAL.
  5. SQLCODE 100 gives 01. Any other code gives 90 and a log entry.
graph TD A[OPEN cursor] --> B{SQLCODE = 0} B -- No --> C[Return code 89, log error] B -- Yes --> D C --> D[FETCH row, DO UNTIL SQLCODE greater than 0] D --> E{SQLCODE = 0} E -- Yes --> F[Convert and copy row
count records for 03ICOM] F --> G{Record count above 20} G -- Yes --> H[Force SQLCODE = 17 to end loop] G -- No --> D E -- No --> I[CLOSE cursor] H --> I I --> J{CLOSE SQLCODE = 0} J -- No --> K[Return code 88, log error] J -- Yes --> L[03ICOM only: PUT CONTAINER
ICOM-Data and ICOM-Count]

The multi-row routines behave differently:

  • 03ICOM. Builds up to 1202-byte records one after another in the container area. It puts ICOM-Data (record count × 1202 bytes) and a 2-byte ICOM-Count on channel ICOM. The cap is checked after the 21st row is stored.
  • 05ICOM and 02ICLM. Each fetch overwrites the same COMMAREA position, so only the last row survives. They have no row cap and no containers.
  • Cursor attributes. All three cursors are declared as insensitive scroll.
  • Empty results. Cursors that return no rows do not set 01.

5.3 LGUPDB01: Update Policy

LGUPDB01 is the only program that uses a FOR UPDATE cursor and optimistic locking. POLICY_CURSOR is declared WITH HOLD ... FOR UPDATE OF ISSUEDATE, EXPIRYDATE, LASTCHANGED, BROKERID, BROKERSREFERENCE. It is keyed on customer and policy number.

sequenceDiagram participant Caller as LGUPOL01 participant U as LGUPDB01 participant DB as Db2 participant V as LGUPVS01 Caller->>U: LINK COMMAREA (CA_LASTCHANGED as read earlier) U->>DB: OPEN POLICY_CURSOR U->>DB: FETCH row (indicators for nullable columns) alt SQLCODE 100 U->>U: Return code 01 else CA_LASTCHANGED differs from DB2_LASTCHANGED U->>U: Return code 02, no update else timestamps match U->>DB: UPDATE ENDOWMENT / HOUSE / MOTOR by CA_REQUEST_ID U->>DB: UPDATE POLICY WHERE CURRENT OF POLICY_CURSOR U->>DB: SELECT LASTCHANGED into CA_LASTCHANGED end U->>DB: CLOSE POLICY_CURSOR U->>V: LINK 225 bytes U-->>Caller: RETURN

The routing and positioned update:

PLI 
SELECT (CA_REQUEST_ID);
   WHEN ('01UEND') CALL UPDATE_ENDOW_DB2_INFO;
   WHEN ('01UHOU') CALL UPDATE_HOUSE_DB2_INFO;
   WHEN ('01UMOT') CALL UPDATE_MOTOR_DB2_INFO;
END;

EXEC SQL UPDATE POLICY
   SET ISSUEDATE = :CA_ISSUE_DATE, EXPIRYDATE = :CA_EXPIRY_DATE,
       LASTCHANGED = CURRENT TIMESTAMP,
       BROKERID = :DB2_BROKERID_INT,
       BROKERSREFERENCE = :CA_BROKERSREF
 WHERE CURRENT OF POLICY_CURSOR;

The type-specific update runs before the POLICY update. If it leaves the return code other than 00, the program closes the cursor and returns without updating POLICY. If the post-update SELECT LASTCHANGED fails, the program issues EXEC CICS SYNCPOINT ROLLBACK, which also undoes the type-table update. It then sets 90 and logs.

5.4 LGDPDB01: Delete Policy

LGDPDB01 accepts four request codes: 01DEND, 01DHOU, 01DCOM and 01DMOT. All four run the same statement against POLICY only. Foreign-key cascade removes the matching child row, so the program issues no explicit delete against the type tables.

PLI 
EM_SQLREQ = ' DELETE POLICY  ';
EXEC SQL DELETE FROM POLICY
   WHERE CUSTOMERNUMBER = :DB2_CUSTOMERNUM_INT
     AND POLICYNUMBER   = :DB2_POLICYNUM_INT;
IF SQLCODE ^= 0 THEN DO;
   CA_RETURN_CODE = '90';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS RETURN;
END;

On success, the program links to LGDPVS01 with 32,500 bytes. On failure it returns before that link, so the VSAM copy is never deleted when Db2 fails. The source comment says SQLCODE 100 should count as success, but the test is SQLCODE <> 0. A delete that finds no row therefore returns 90.

7. Cursors, Locking and Foreign-Key Behaviour

7.1 Cursor Summary

Cursor Program Purpose Options
POLICY_CURSOR LGUPDB01 Lock and fetch one POLICY row WITH HOLD, FOR UPDATE OF five columns
Cust_Cursor LGIPDB01 Commercial policies of a customer Insensitive scroll
Zip_Cursor LGIPDB01 Commercial policies by Zipcode Insensitive scroll
CusClaim_Cursor LGIPDB01 Claims of a customer Insensitive scroll

LGUPDB01 handles two cursor SQLCODEs explicitly. On OPEN, -913 and any other non-zero code give 90 and an immediate return. On CLOSE, 0 and -501 (cursor not open) give 00. The close step always overwrites the return code with 00 on success, so a 01 or 02 set earlier can be lost.

7.2 Foreign Keys and Cascades

  • Parent before child. LGAPDB01 inserts the POLICY row first and reads the generated number with IDENTITY_VAL_LOCAL(). The type-table insert uses it as the foreign key.
  • Customer must exist. SQLCODE -530 on the POLICY insert means the customer number does not exist. LGAPDB01 and LGACUS01 report it as return code 70.
  • Delete cascade. LGDPDB01 and LGACUS01 delete only the POLICY row. The database cascade removes the child rows in ENDOWMENT, HOUSE, MOTOR and COMMERCIAL. The delete program does not name CLAIM. The cascade must be defined in the schema, because the programs do not enforce it.

7.3 Unit of Work

Program Backout mechanism
LGAPDB01 ABEND LGSQ NODUMP after any SQL failure that follows the POLICY insert
LGUPDB01 EXEC CICS SYNCPOINT ROLLBACK when the final POLICY update or read-back fails
All others None explicit. The unit of work ends with the CICS task, and the task is not abended on SQL errors

8.2 SQLCODE Interpretation

SQLCODE Where handled Result
0 All programs Success path
100 LGICDB01, LGUCDB01, LGIPDB01, LGUPDB01 01, no log entry. Delete programs treat 100 as an error
-530 LGAPDB01, LGACUS01 (policy insert) 70 plus log
-913 LGICDB01 01 (same as not found). LGUPDB01 treats it like any other open failure (90)
-501 LGUPDB01 (close) Treated as benign (00)
-305 None handled (no indicators in LGICDB01) Falls to 90. LGIPDB01 uses indicators to avoid it
anything else All programs 90 (or 98 in LGACDB02), plus a log entry

9. Links to the VSAM Programs and Helpers

Db2 program Linked program COMMAREA When
LGACDB01, LGACUS01 LGACVS01 COMM_AREA, 225 bytes After the customer insert
LGACDB01, LGACUS01 LGACDB02 CDB2AREA, 32,500 bytes After the VSAM link; adds the security row
LGUCDB01 LGUCVS01 COMM_AREA, 225 bytes Always, even after 01 or 90
LGAPDB01 LGAPVS01 COMM_AREA, 32,500 bytes After all inserts succeed
LGUPDB01 LGUPVS01 COMM_AREA, 225 bytes After UPDATE_POLICY_DB2_INFO; skipped by the early RETURNs
LGDPDB01 LGDPVS01 COMM_AREA, 32,500 bytes Only after a successful Db2 delete
All LGSTSQ ERROR_MSG / CA_ERROR_MSG Every error path

Typical link code:

PLI 
EXEC CICS LINK PROGRAM('LGUCVS01')
     COMMAREA(COMM_AREA) LENGTH(225);
EXEC CICS RETURN;

None of the VSAM links is checked for RESP. A VSAM failure is visible only if the linked program reports it in the shared COMMAREA.

10. Observations and Maintenance Notes

  • Unreachable operations. LGACUS01 never changes ACTION_CODE from '0', so no customer or policy operation runs.
  • Delete semantics. The comments in LGDPDB01 and LGACUS01 say SQLCODE 100 is success, but the code returns 90.
  • Return code 98 is overloaded. It means “COMMAREA too short” in most programs and “insert failed” in LGACDB02.
  • Lost return codes. LGUPDB01 overwrites 01 and 02 with 00 in CLOSE_PCURSOR. LGUCDB01 links to the VSAM program even when Db2 reported a problem.
  • House update code. LGUPDB01 sets 01 for every non-zero SQLCODE in the house update, so a real Db2 error looks like “not found”.
  • Endowment update. In LGUPDB01, the variable-length branch has no SQLCODE check. The padding data is staged in a work area but is not part of the UPDATE ENDOWMENT statement.
  • Error-message program tag. LGUPDB01 carries LGIPOL01 as the program tag in its error messages, and LGIPDB01 does the same.
  • Link length in logging. LGDPDB01 passes LENGTH(STG(ERROR_MSG)) on the COMMAREA-dump link, which may differ from the length of CA_ERROR_MSG.
  • Length constants. The header lengths (18, 28, 33) and link lengths (225, 32,500) are hard-coded and duplicated across programs. They must be kept consistent with LGCMAREA and LGPOLICY.
  • Result limits in LGIPDB01. Only 03ICOM limits rows (about 20) and returns them through containers. 05ICOM and 02ICLM return only the last row fetched.
