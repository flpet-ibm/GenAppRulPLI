Customer Creation and Security Registration

1. Overview

Customer onboarding in the GenApp general insurance application creates the customer in three places. These are the Db2 CUSTOMER table, the VSAM KSDS file KSDSCUST, and the Db2 CUSTOMER_SECURE table, which holds the customer’s initial credentials. Each place is handled by its own CICS-hosted Enterprise PL/I program. A shared error-logging program, LGSTSQ, supports all of them.

Step Program What it does
1 LGACDB01 (standalone) or LGACUS01 (ONBOARD_CUSTOMER) Validates the COMMAREA, allocates a customer number, and inserts the CUSTOMER row in Db2.
2 LGACVS01 Writes the customer record to the VSAM KSDS KSDSCUST, keyed on the customer number.
3 LGACDB02 Inserts the CUSTOMER_SECURE row with a default password hash, state N and a change count of 0000.

The customer number comes from the CICS named counter GENACUSTNUM in pool GENA. If the counter cannot be read, the program silently falls back to the Db2 identity column (DEFAULT plus IDENTITY_VAL_LOCAL()).

This page covers the application-level flow, the data contracts between the programs, the return codes, and the error behaviour.

2. System Architecture

2.1 Component View

graph TD Caller[Calling transaction or program] --> ORCH subgraph ONB [Onboarding programs] ORCH[LGACDB01 or LGACUS01 ONBOARD_CUSTOMER] VS[LGACVS01 VSAM customer writer] SEC[LGACDB02 customer security writer] LOG[LGSTSQ error logger] end ORCH -->|GET COUNTER| NC[(Named counter GENACUSTNUM pool GENA)] ORCH -->|INSERT INTO CUSTOMER| DB1[(Db2 CUSTOMER)] ORCH -->|LINK COMMAREA 225 bytes| VS ORCH -->|LINK CDB2AREA 32500 bytes| SEC VS -->|WRITE FILE KSDSCUST| KS[(VSAM KSDS KSDSCUST)] SEC -->|INSERT INTO CUSTOMER_SECURE| DB2[(Db2 CUSTOMER_SECURE)] ORCH -.->|errors| LOG VS -.->|errors| LOG SEC -.->|errors| LOG LOG --> Q[(CICS TD/TS queues)]

The orchestrating program owns the sequence. It allocates the key, writes the primary Db2 row, and then drives the two downstream writers by EXEC CICS LINK. Each downstream program does one write and reports problems through LGSTSQ.

2.2 Component Responsibilities

Component Type Responsibility
LGACDB01 CICS PL/I main program Adds a customer to Db2, then links to LGACVS01 and LGACDB02. It supplies a fixed default password hash.
LGACUS01 CICS PL/I main program Multi-action service (add customer, offer, transfer, delete policy). The add-customer branch, ONBOARD_CUSTOMER, follows the same onboarding pattern.
LGACVS01 CICS PL/I main program Writes the customer record to the VSAM KSDS KSDSCUST.
LGACDB02 CICS PL/I main program Inserts the CUSTOMER_SECURE row. It accepts only request ID 02ACUS.
LGSTSQ Shared logging program Receives ERROR_MSG and CA_ERROR_MSG records and writes them to CICS queues.
GENACUSTNUM / GENA CICS named counter Source of unique customer numbers.
CUSTOMER Db2 table Master customer record.
CUSTOMER_SECURE Db2 table Per-customer credential record.
KSDSCUST VSAM KSDS Customer record keyed on the 10-digit customer number.

2.3 Entity Relationships

erDiagram CUSTOMER ||--o| CUSTOMER_SECURE : "has credentials" CUSTOMER ||--o| KSDSCUST : "mirrored as VSAM record" CUSTOMER ||--o{ POLICY : "holds" CUSTOMER { int CUSTOMERNUMBER "from counter or identity" string FIRSTNAME string LASTNAME string DATEOFBIRTH string HOUSENAME string HOUSENUMBER string POSTCODE string PHONEMOBILE string PHONEHOME string EMAILADDRESS } CUSTOMER_SECURE { int customerNumber "from CA_CUSTOMER_NUM" string customerPass "32 chars" string state_indicator "1 char" int pass_changes "from CA_CUSTSECR_COUNT" } KSDSCUST { string CA_CUSTOMER_NUM "VSAM key, 10 bytes" } POLICY { int POLICYNUMBER int CUSTOMERNUMBER }

All three representations of a customer share the same customer number. That number is the Db2 key, the VSAM record key and the security-record key.

3. Request Contract

3.1 COMMAREA Layout and Validation

All programs share the COMM_AREA layout from LGCMAREA. It is a based structure of 32,500 bytes. It has a fixed header followed by a union of request-specific layouts: customer, customer security and policy.

Field Format Use in onboarding
CA_REQUEST_ID CHAR(6) Identifies the request. 02ACUS is used for the security link.
CA_RETURN_CODE PIC ‘99’ Status returned to the caller.
CA_CUSTOMER_NUM PIC ‘9999999999’ Output of the Db2 insert. Also the VSAM key and the security key.
CA_FIRST_NAME, CA_LAST_NAME, CA_DOB CHAR 10, 20, 10 Customer identity.
CA_HOUSE_NAME, CA_HOUSE_NUM, CA_POSTCODE CHAR 20, 4, 8 Address.
CA_PHONE_MOBILE, CA_PHONE_HOME, CA_EMAIL_ADDRESS CHAR 20, 20, 100 Contact details.
CA_CUSTSECR_PASS, CA_CUSTSECR_COUNT, CA_CUSTSECR_STATE CHAR 32, 4, 1 Security request, used by LGACDB02.

Before doing any work, the onboarding program validates the COMMAREA length:

  • EIBCALEN = 0: the program logs NO COMMAREA RECEIVED through LGSTSQ, then abends with LGCA (NODUMP).
  • EIBCALEN < 90: the minimum is an 18-byte header plus a 72-byte customer section. The program sets CA_RETURN_CODE to 98 and returns.
  • Otherwise: it sets CA_RETURN_CODE to 00 and continues.
graph TD A([Entry]) --> B{EIBCALEN equals 0?} B -- Yes --> C[Log NO COMMAREA RECEIVED] C --> D([ABEND LGCA NODUMP]) B -- No --> E[Set return code 00] E --> F{EIBCALEN less than 90?} F -- Yes --> G[Set return code 98] G --> H([EXEC CICS RETURN]) F -- No --> I([Proceed to customer creation])

3.2 Entry Points

LGACDB01 is the dedicated add-customer program. It performs validation and then runs the onboarding sequence directly.

LGACUS01 is a multi-action service that dispatches on ACTION_CODE. Action '1' sets CA_REQUEST_ID to 01ICUS and runs ONBOARD_CUSTOMER. In the PL/I source as written, ACTION_CODE is initialised to '0' and never changed. The SELECT therefore falls through to OTHERWISE, and the add-customer branch cannot currently be reached through LGACUS01. The onboarding logic in that branch matches LGACDB01, and the rest of this page describes it.

4. End-to-End Sequence

The sequence below shows a successful onboarding where the named counter is available.

sequenceDiagram participant Caller participant ORCH as LGACDB01 / LGACUS01 participant NC as Named Counter GENACUSTNUM participant DB as Db2 CUSTOMER participant VS as LGACVS01 participant KS as VSAM KSDSCUST participant SEC as LGACDB02 participant DS as Db2 CUSTOMER_SECURE Caller->>ORCH: LINK with COMMAREA (customer details) ORCH->>ORCH: Validate EIBCALEN (>= 90 bytes) ORCH->>NC: EXEC CICS GET COUNTER NC-->>ORCH: Next customer number ORCH->>DB: INSERT INTO CUSTOMER DB-->>ORCH: SQLCODE 0 ORCH->>ORCH: CA_CUSTOMER_NUM = customer number ORCH->>VS: LINK COMMAREA length 225 VS->>KS: WRITE FILE KSDSCUST RIDFLD customer number KS-->>VS: RESP NORMAL VS-->>ORCH: Return ORCH->>ORCH: Build CDB2AREA (02ACUS, 0000, N) ORCH->>SEC: LINK CDB2AREA length 32500 SEC->>DS: INSERT INTO CUSTOMER_SECURE DS-->>SEC: SQLCODE 0 SEC-->>ORCH: Return code 00 ORCH-->>Caller: COMMAREA with new CA_CUSTOMER_NUM and 00

The processing order is fixed:

  1. Validate the COMMAREA.
  2. Allocate the customer number.
  3. Insert the Db2 CUSTOMER row.
  4. Link to LGACVS01 for the VSAM write.
  5. Link to LGACDB02 for the security record.

If the Db2 insert fails, the program returns before either link, so no VSAM or security record is created for that customer.

5. Customer Number Allocation

5.1 Named Counter with Identity Fallback

OBTAIN_CUSTOMER_NUMBER requests the next value from the CICS named counter GENACUSTNUM in pool GENA. The program tracks the outcome in the switch LGAC_NCS, which starts as ON.

graph TD A[EXEC CICS GET COUNTER GENACUSTNUM pool GENA] --> B{WS_RESP equals NORMAL?} B -- Yes --> C[DB2_CUSTOMERNUM_INT = counter value
LGAC_NCS stays ON] B -- No --> D[LGAC_NCS = NO
DB2_CUSTOMERNUM_INT = 0] C --> E[INSERT with explicit CUSTOMERNUMBER] D --> F[INSERT with DEFAULT CUSTOMERNUMBER] F --> G[SET :DB2_CUSTOMERNUM_INT = IDENTITY_VAL_LOCAL] E --> H[CA_CUSTOMER_NUM = DB2_CUSTOMERNUM_INT] G --> H

The fallback is silent. No error message is written, no return code is set, and no abend occurs. The caller cannot tell which numbering source was used.

PLI 
EXEC CICS GET COUNTER(GENACOUNT)      /* 'GENACUSTNUM' */
               POOL(GENAPOOL)         /* 'GENA'        */
               VALUE(LASTCUSTNUM)
               RESP(WS_RESP);

IF WS_RESP = DFHRESP(NORMAL) THEN
   DB2_CUSTOMERNUM_INT = LASTCUSTNUM;
ELSE DO;
   LGAC_NCS = 'NO';
   DB2_CUSTOMERNUM_INT = 0;
END;

6. Db2 CUSTOMER Insert

INSERT_CUSTOMER sets the SQL request label to INSERT CUSTOMER (used in error messages) and chooses one of two insert forms.

LGAC_NCS CUSTOMERNUMBER source After the insert
ON :DB2_CUSTOMERNUM_INT (from the counter) Value is already known.
NO DEFAULT (Db2 identity) SET :DB2_CUSTOMERNUM_INT = IDENTITY_VAL_LOCAL()

The remaining columns come directly from the COMMAREA fields: CA_FIRST_NAME, CA_LAST_NAME, CA_DOB, CA_HOUSE_NAME, CA_HOUSE_NUM, CA_POSTCODE, CA_PHONE_MOBILE, CA_PHONE_HOME and CA_EMAIL_ADDRESS.

PLI 
IF LGAC_NCS = 'ON' THEN DO;
   EXEC SQL INSERT INTO CUSTOMER
        ( CUSTOMERNUMBER, FIRSTNAME, LASTNAME, DATEOFBIRTH,
          HOUSENAME, HOUSENUMBER, POSTCODE,
          PHONEMOBILE, PHONEHOME, EMAILADDRESS )
        VALUES
        ( :DB2_CUSTOMERNUM_INT, :CA_FIRST_NAME, :CA_LAST_NAME, :CA_DOB,
          :CA_HOUSE_NAME, :CA_HOUSE_NUM, :CA_POSTCODE,
          :CA_PHONE_MOBILE, :CA_PHONE_HOME, :CA_EMAIL_ADDRESS );
END;
ELSE DO;
   /* same INSERT, but with DEFAULT for CUSTOMERNUMBER */
   EXEC SQL SET :DB2_CUSTOMERNUM_INT = IDENTITY_VAL_LOCAL();
END;

IF SQLCODE ^= 0 THEN DO;
   CA_RETURN_CODE = '90';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS RETURN;
END;
CA_CUSTOMER_NUM = DB2_CUSTOMERNUM_INT;

The SQLCODE check applies to both insert forms. Any non-zero SQLCODE sets return code 90, logs the error, and returns to the caller without linking to the downstream programs.

7. VSAM Record Write (LGACVS01)

7.1 Behaviour

After the Db2 insert, the orchestrator links to LGACVS01 with the full COMMAREA and a length of 225. LGACVS01 writes the customer record to the VSAM KSDS KSDSCUST. CA_CUSTOMER_NUM is both the start of the data written and the 10-byte record key.

PLI 
WS_Commarea_Len = EIBCALEN;

EXEC CICS WRITE FILE('KSDSCUST')
               FROM(CA_Customer_Num)
               LENGTH(WS_Commarea_Len)
               RIDFLD(CA_Customer_Num)
               KEYLENGTH(10)
               RESP(WS_RESP);
graph TD A([Start LGACVS01]) --> B[WS_Commarea_Len = EIBCALEN] B --> C[EXEC CICS WRITE FILE KSDSCUST] C --> D{RESP equals NORMAL?} D -- Yes --> E([RETURN]) D -- No --> F[Save EIBRESP2 in WS_RESP2] F --> G[CA_RETURN_CODE = 80] G --> H[WRITE_ERROR_MESSAGE: two links to LGSTSQ] H --> I([ABEND LGV0 NODUMP])

7.2 Failure Handling

LGACVS01 makes no distinction between failure causes. A duplicate key (DUPREC), a closed or disabled file, an I/O error or a length error all follow the same path:

  1. Capture EIBRESP2.
  2. Set CA_RETURN_CODE to 80.
  3. Log the error and a COMMAREA snapshot through LGSTSQ.
  4. Abend the task with LGV0 and no dump.

The abend means the caller will not normally see return code 80. CICS backs out recoverable resources in the unit of work. The Db2 insert is one of these, so a VSAM failure should roll it back along with the work the task has done so far.

The ERROR_MSG written for a VSAM failure has this form:

CODE 
05152024   10:32:45 LGACVS01 CNUM=0000000123 Write file KSDSCUST RESP=   +14 RESP2=    +0

8. Security Registration (LGACDB02)

8.1 Building the Security Request

Once the VSAM write succeeds, the orchestrator populates the security area CDB2AREA and links to LGACDB02 with a length of 32,500.

CDB2AREA field Value
D2_CUSTOMER_NUM The newly allocated customer number.
D2_REQUEST_ID 02ACUS (add customer security).
D2_CUSTSECR_PASS In LGACDB01, the fixed hash 5732fec825535eeafb8fac50fee3a8aa.
D2_CUSTSECR_COUNT 0000
D2_CUSTSECR_STATE N (new)

LGACUS01 sets the customer number, request ID, count and state in the same way. Its description does not mention the password field explicitly.

PLI 
D2_CUSTOMER_NUM    = DB2_CUSTOMERNUM_INT;
D2_REQUEST_ID      = '02ACUS';
D2_CUSTSECR_PASS   = '5732fec825535eeafb8fac50fee3a8aa';
D2_CUSTSECR_COUNT  = '0000';
D2_CUSTSECR_STATE  = 'N';

EXEC CICS LINK PROGRAM('LGACDB02')
               COMMAREA(CDB2AREA)
               LENGTH(32500);

8.2 Insert into CUSTOMER_SECURE

LGACDB02 accepts only request ID 02ACUS. Any other value sets return code 99 and returns, with no database activity. For 02ACUS, it copies the customer number and the 4-character count into integer host variables and inserts one row.

PLI 
SELECT (CA_REQUEST_ID);
   WHEN ('02ACUS') DO;
      DB2_CUSTOMERNUM_INT = CA_CUSTOMER_NUM;
      DB2_CUSTOMERCNT_INT = CA_CUSTSECR_COUNT;
      CALL INSERT_CUSTOMER_PASSWORD;
   END;
   OTHERWISE DO;
      CA_RETURN_CODE = '99';
      EXEC CICS RETURN;
   END;
END;
PLI 
EM_SQLREQ = ' INSERT SECURITY';
EXEC SQL INSERT INTO CUSTOMER_SECURE
     ( customerNumber, customerPass, state_indicator, pass_changes )
     VALUES
     ( :DB2_CUSTOMERNUM_INT, :CA_CUSTSECR_PASS,
       :CA_CUSTSECR_STATE,   :DB2_CUSTOMERCNT_INT );

IF SQLCODE ^= 0 THEN DO;
   CA_RETURN_CODE = '98';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS RETURN;
END;
graph TD A([Start LGACDB02]) --> B{EIBCALEN equals 0?} B -- Yes --> C[Log error] --> D([ABEND LGCA]) B -- No --> E[Return code 00] E --> F{Request ID is 02ACUS?} F -- No --> G[Return code 99] --> H([RETURN]) F -- Yes --> I[Convert customer number and count] I --> J[INSERT INTO CUSTOMER_SECURE] J --> K{SQLCODE zero?} K -- Yes --> L([RETURN code 00]) K -- No --> M[Return code 98, log error] --> N([RETURN])

8.3 Credential Defaults

The state N marks the password as new. The change count starts at 0000. The password column is 32 characters and by default holds an MD5-style checksum. Working-storage defaults such as WS_CS_PASSWORD ('NewPass') are declared in the programs, but the values actually inserted come from the COMMAREA or CDB2AREA that the caller builds.

9. Return Codes and Error Handling

9.1 Return Code Summary

Code Set by Meaning
00 LGACDB01, LGACUS01, LGACDB02 Success.
80 LGACVS01 VSAM write to KSDSCUST failed (followed by abend LGV0).
90 LGACDB01, LGACUS01 Db2 CUSTOMER insert failed.
98 LGACDB01, LGACUS01 COMMAREA shorter than 90 bytes.
98 LGACDB02 Insert into CUSTOMER_SECURE failed.
99 LGACDB02 Request ID is not 02ACUS.

Return code 98 is used for two different failures. The onboarding programs use it for a short COMMAREA, and LGACDB02 uses it for a database insert failure. Callers need to know which program set it.

9.2 Abends

Abend Program Condition
LGCA LGACDB01, LGACUS01, LGACDB02 No COMMAREA received (EIBCALEN = 0). Issued with NODUMP.
LGV0 LGACVS01 VSAM write returned a non-NORMAL response. Issued with NODUMP.

9.3 Failure Paths Through the Flow

graph TD S([Onboarding request]) --> V{COMMAREA valid?} V -- "length 0" --> A1([ABEND LGCA]) V -- "length under 90" --> R98([Return 98]) V -- OK --> N[Allocate number] N --> I{Db2 CUSTOMER insert OK?} I -- No --> R90([Return 90, no downstream links]) I -- Yes --> W[LINK LGACVS01] W --> WV{VSAM write OK?} WV -- No --> A2([Return code 80, ABEND LGV0]) WV -- Yes --> L[LINK LGACDB02] L --> LV{Security insert OK?} LV -- "99" --> R99([Unsupported request]) LV -- "98" --> R98b([Security insert failed]) LV -- "00" --> OK([Customer fully registered])

9.4 Error Logging

Every error path calls WRITE_ERROR_MESSAGE, except the silent named-counter fallback and the short-COMMAREA return in the onboarding programs. The routine does the following:

  1. Stores the SQLCODE in EM_SQLRC, where the program has one.
  2. Issues EXEC CICS ASKTIME, then FORMATTIME to get the date (MMDDYYYY) and time.
  3. Links to LGSTSQ with ERROR_MSG, which holds the date, time, program name, customer number, policy number, SQL request label and SQLCODE.
  4. If EIBCALEN > 0, links to LGSTSQ a second time with CA_ERROR_MSG. This holds the prefix COMMAREA= plus up to the first 90 bytes of the COMMAREA.
PLI 
IF EIBCALEN > 0 THEN DO;
   IF EIBCALEN < 91 THEN
      CA_DATA = LEFT(COMM_AREA_RAW, EIBCALEN);
   ELSE
      CA_DATA = LEFT(COMM_AREA_RAW, 90);
   EXEC CICS LINK PROGRAM('LGSTSQ')
                  COMMAREA(CA_ERROR_MSG)
                  LENGTH(STG(CA_ERROR_MSG));
END;

Each program uses an eyecatcher in its working storage (for example LGACDB01------WS) to help identify it in a dump.

10. Design Considerations and Observations

10.1 Data Consistency Across Stores

  • Customer creation spans three stores. The Db2 CUSTOMER insert and the CUSTOMER_SECURE insert are Db2 changes, and the VSAM write is a file-control change. The programs issue no explicit commit or rollback, so consistency relies on CICS unit-of-work handling at task end or syncpoint.
  • The VSAM-failure abend (LGV0) lets CICS back out the unit of work. A failure in LGACDB02 returns normally with 98 and no abend. The orchestrator then has to act on the code, as described in 10.2.

10.2 Return Code Propagation

  • In LGACDB01, CDB2AREA and COMM_AREA are separate areas. The return code from LGACDB02 is not copied back into CA_RETURN_CODE. The check after the LGACDB02 link therefore tests a value set earlier in the program, and both outcomes end in EXEC CICS RETURN. A failure to create the security record is not reflected in the caller’s COMMAREA.
  • The result of the LGACVS01 link is not checked directly. A VSAM failure ends the task through the LGV0 abend instead.

10.3 Other Notes

  • Customer number source: the named counter is preferred. The identity column is a silent fallback, so both can supply numbers in the same environment. They can collide unless the two sources are kept in step.
  • VSAM record length: LGACVS01 writes EIBCALEN bytes starting at CA_CUSTOMER_NUM. The link passes 225 bytes, so the record includes whatever follows the key in the COMMAREA. No minimum or maximum length check is made.
  • Logging calls: the LINK calls to LGSTSQ have no RESP handling. If the program is unavailable, default CICS condition handling applies.
  • Input validation: the programs check only COMMAREA length. Field content such as date format or numeric content of the password count is not validated. CA_CUSTSECR_COUNT is a CHAR(4) field converted implicitly to a binary integer, so non-numeric content would raise a conversion error.

11. Examples

11.1 Successful Onboarding with the Named Counter

Input

Field Value
CA_REQUEST_ID 01ACUS
CA_FIRST_NAME / CA_LAST_NAME John / Smith
CA_DOB 1985-05-15
CA_POSTCODE AB12 3CD
GENACUSTNUM returns 1000001 (NORMAL)

Result

  • A CUSTOMER row is inserted with CUSTOMERNUMBER = 1000001.
  • CA_CUSTOMER_NUM becomes 0001000001.
  • LGACVS01 writes the VSAM record with key 0001000001.
  • LGACDB02 inserts the CUSTOMER_SECURE row with state N and pass_changes = 0.
  • CA_RETURN_CODE is 00.

11.2 Counter Unavailable: Identity Fallback

The GET COUNTER call returns a non-NORMAL response. LGAC_NCS becomes NO and the customer number is set to 0. The CUSTOMER insert uses DEFAULT for CUSTOMERNUMBER. If Db2 generates 2000055, IDENTITY_VAL_LOCAL() returns that value. The value is stored in CA_CUSTOMER_NUM and used for the VSAM key and the security record. The return code is 00, and no message is logged for the fallback.

11.3 COMMAREA Too Short

EIBCALEN = 50, which is below the required 90 bytes. The program sets CA_RETURN_CODE to 98 and returns. No counter is read, and nothing is written to Db2, VSAM or the error queue.

11.4 Duplicate Key on the VSAM Write

The customer number 0000000123 already exists in KSDSCUST:

  • LGACVS01 receives a non-NORMAL response (DUPREC).
  • It sets CA_RETURN_CODE to 80 and logs two messages through LGSTSQ. The first holds CNUM, RESP and RESP2. The second holds COMMAREA= plus up to 90 bytes of the data.
  • It abends with LGV0, and CICS backs out the unit of work. LGACDB02 is never reached.

11.5 Security Insert Failure

The Db2 insert into CUSTOMER_SECURE fails, for example on a duplicate key for customer 12345:

  • LGACDB02 sets CA_RETURN_CODE to 98.
  • It logs the failure with the label INSERT SECURITY, then returns.
  • The CUSTOMER row and the VSAM record already exist. As noted in section 10.2, the orchestrator does not automatically see this code in its own COMMAREA.

11.6 Unsupported Security Request ID

A caller links to LGACDB02 with CA_REQUEST_ID = 01ICUS. The SELECT takes the OTHERWISE branch, the program sets return code 99 and returns, and nothing is written to Db2 or the error queue.
