Transaction Statistics Collection

1. Overview

Transaction Statistics Collection monitors transaction volumes in the GenApp CICS application. It has two cooperating PL/I programs.

Program Role Trigger
LGASTAT1 Event-processing adapter target. It counts how often each business request type completes with a given outcome. Each time CICS event processing (or a calling program, through the COMMAREA) reports a completed request
LGWEBST5 Periodic aggregator that runs as transaction SSST. It reads all counters, totals them by category and calculates deltas. It writes the results to temporary storage (TS) queues. Reschedules itself every minute

The programs share one resource, the CICS named counter pool GENA. LGASTAT1 increments counters in it. LGWEBST5 reads them without changing them and turns the cumulative totals into current, previous and delta values for display or monitoring.

The main characteristics of the design are:

  • Counter granularity: There is one counter per request type and outcome. Outcomes are reduced to success (00) or failure (99).
  • Legacy code consolidation: Variant request codes are folded into one canonical counter.
  • Start marker: A one-time TS queue record (GENASTRT) marks when collection began.
  • Self-perpetuating collection: LGWEBST5 restarts itself with EXEC CICS START TRANSID('SSST') AFTER MINUTES(1).
  • Rate data: Each monitored value is stored as a three-item queue holding the new value, the old value and the delta.

3. Event Capture with LGASTAT1

3.1 Purpose and Input Sources

LGASTAT1 counts completed business requests. It reads its input from one of two places, in this order of precedence:

  1. Event-processing channel containers, primary source:
    • DFHEP.DATA.00001 holds the 6-character request ID (WS_DATA_REQ).
    • DFHEP.DATA.00002 holds the 2-character return code (WS_DATA_RC).
  2. COMMAREA, fallback source:
    • CA_REQUEST_ID is the 6-character request ID.
    • CA_RETURN_CODE is the 2-digit return code.

Both GET CONTAINER commands use the same WS_RESP field. The second response overwrites the first, so only the second read decides which source is used. If the containers are not available and EIBCALEN is 0, the program issues EXEC CICS RETURN immediately without updating any counter.

3.3 Request and Outcome Normalisation

Legacy and variant request codes are consolidated so that they count against one counter. Every failure is collapsed into a single outcome, which keeps the number of counters bounded.

Incoming request Normalised request
02ACUS 01ACUS
02ICOM, 03ICOM, 05ICOM 01ICOM
Anything else Unchanged
Incoming return code Normalised outcome
00 00 (success)
Any other value 99 (failure)

The following snippet illustrates the rules in PL/I-style pseudocode:

PLI 
IF GENACOUNTER = '02ACUS' THEN
   GENACOUNTER = '01ACUS';
IF GENACOUNTER = '02ICOM' | GENACOUNTER = '03ICOM' |
   GENACOUNTER = '05ICOM' THEN
   GENACOUNTER = '01ICOM';
IF GENATYPE ^= '00' THEN
   GENATYPE = '99';

3.4 Counter Name Structure

The counter name passed to GET COUNTER is exactly 16 characters long.

Bytes Content Field
1–4 Prefix GENA constant
5–10 Request identifier GENACOUNTER
11–12 Outcome (00 or 99) GENATYPE
13–16 Blank padding filler

For example, a successful commercial request produces GENA01ICOM00 . GET COUNTER returns the next value and increments the counter, so each call adds 1 to the total for that request and outcome. The returned value goes to TRANCOUNT, which is a fullword (FIXED BIN(31)). No other part of the program uses it.

3.5 Statistics Start Marker

On every invocation LGASTAT1 reads queue GENASTRT. The queue is written only when the read returns QIDERR, so it records when the first statistic was captured. The 16-byte record is laid out as follows:

Bytes Field Content
1–8 WS_AREA_D Date (from FORMATTIME, DDMMYYYY)
9–10 filler Two blanks
11–16 WS_AREA_T Time (HHMMSS)

4. Aggregation with LGWEBST5

4.1 Overview of the Collection Cycle

LGWEBST5 runs as transaction SSST. In each cycle it does the following:

  1. Captures the EIB fields (EIBTRNID, EIBTRMID, EIBTASKN, EIBCALEN) in WS_HEADER for dump identification. The header has the eyecatcher LGWEBST5------WS.
  2. Calls ASKTIME and FORMATTIME to get the date and time.
  3. Calls TRAN_RATE_INTERVAL to compute the elapsed seconds and schedule the next run.
  4. Zeroes the six accumulators: COUNTSUCCESS, COUNTERRORS, COUNTINQ, COUNTADD, COUNTUPD and COUNTDEL.
  5. Queries GENACUSTNUM and records its rate queue GENAX05V.
  6. Loops over 17 success and error counter pairs.
  7. Writes five aggregate rate queues (GENAX00V–GENAX04V).
  8. Issues EXEC CICS RETURN.

4.2 Overall Flow

graph TD A([Start LGWEBST5]) --> B[Capture EIB fields] B --> C[ASKTIME and FORMATTIME] C --> D[TRAN_RATE_INTERVAL] D --> E[Zero accumulators] E --> F[QUERY COUNTER GENACUSTNUM] F --> G[TRAN_RATE_COUNTS for GENAX05V] G --> H[I = 1] H --> I[QUERY COUNTER CT_SUCCESS I] I --> J[Add to COUNTSUCCESS] J --> K{CT_OPS at I} K -- I --> L[COUNTINQ] K -- A --> M[COUNTADD] K -- U --> N[COUNTUPD] K -- D --> O[COUNTDEL] L --> P[TRAN_RATE_COUNTS for GENA code V] M --> P N --> P O --> P P --> Q[QUERY COUNTER CT_ERROR I] Q --> R[Add to COUNTERRORS] R --> S{I < 17?} S -- Yes --> H S -- No --> T[TRAN_RATE_COUNTS for GENAX00V to GENAX04V] T --> U([RETURN])

4.3 Counter Table

The 17 monitored operations are held in four parallel structures: CT_SUCCESS, CT_ERROR, CT_CODE and CT_OPS.

  • CT_SUCCESS names follow GENA01<op><entity>00.
  • CT_ERROR names follow GENA01<op><entity>99.
  • CT_CODE supplies the 3-character rate queue code, from 100 to H00.
  • CT_OPS is the 17-character string IAIADUIADUIADUIAD. Each position classifies the counter at the same index as Inquire, Add, Update or Delete.

The operations covered are:

Entity Operations
Customer Inquire, Add
Motor Inquire, Add, Delete, Update
Endowment Inquire, Add, Delete, Update
House Inquire, Add, Delete, Update
Commercial Inquire, Add, Delete

The routing into sub-totals is a SELECT on SUBSTR(CT_OPS,I,1). A simplified rendering of the logic:

PLI 
DO I = 1 TO 17;
   /* QUERY COUNTER CT_SUCCESS(I) in pool GENA -> COUNTVAL */
   COUNTSUCCESS = COUNTSUCCESS + COUNTVAL;
   SELECT (SUBSTR(CT_OPS,I,1));
      WHEN ('I') COUNTINQ = COUNTINQ + COUNTVAL;
      WHEN ('A') COUNTADD = COUNTADD + COUNTVAL;
      WHEN ('U') COUNTUPD = COUNTUPD + COUNTVAL;
      WHEN ('D') COUNTDEL = COUNTDEL + COUNTVAL;
      OTHERWISE;
   END;
   WS_TSQNAME = TSQPRE || CT_CODE(I) || 'V';
   CALL TRAN_RATE_COUNTS;
   /* QUERY COUNTER CT_ERROR(I) in pool GENA -> COUNTVAL */
   COUNTERRORS = COUNTERRORS + COUNTVAL;
END;

4.4 Interval Calculation (TRAN_RATE_INTERVAL)

This procedure does the following:

  1. Reads item 1 of GENA000V into WS_OLDV. If the read fails, as on the first run, it defaults to 120000 (12:00:00).
  2. Deletes GENA000V and writes the current HHMMSS as item 1.
  3. Converts the new and old times to seconds with HH×3600 + MM×60 + SS.
  4. Sets ICOUNTVAL = ABS(NCOUNTVAL - OCOUNTVAL), stores it in WS_NEWV and writes it as item 2.
  5. Reschedules the transaction:
PLI 
EXEC CICS START TRANSID('SSST')
          AFTER MINUTES(1)
          RESP(WS_RESP);

The restart is issued in this procedure, before any counter is queried. The next cycle is therefore always scheduled, even when later steps fail silently.

4.5 Rate Recording (TRAN_RATE_COUNTS)

This reusable procedure maintains the three-item history for each monitored value.

sequenceDiagram participant P as TRAN_RATE_COUNTS participant Q as TS Queue WS_TSQNAME P->>Q: READQ TS item 1 (9 bytes) alt RESP NORMAL Q-->>P: Previous value -> ORATEVAL else Queue missing P->>P: ORATEVAL = 0 end P->>Q: DELETEQ TS P->>Q: WRITEQ TS item 1 = NRATEVAL (new) P->>Q: WRITEQ TS item 2 = ORATEVAL (old) P->>P: DRATEVAL = ABS(NRATEVAL - ORATEVAL) P->>Q: WRITEQ TS item 3 = DRATEVAL (delta)

Because the queue is deleted before each rewrite, the new value is always item 1, the old value item 2 and the delta item 3. Consumers of the queue depend on this order.

4.6 Aggregate Queues

Queue Content
GENAX00V Total successful transactions (COUNTSUCCESS)
GENAX01V Total inquiries (COUNTINQ)
GENAX02V Total adds (COUNTADD)
GENAX03V Total updates (COUNTUPD)
GENAX04V Total deletes (COUNTDEL)
GENAX05V Customer-number counter GENACUSTNUM

COUNTERRORS is accumulated but is not written to any queue by this program.

7. Dependencies

7.1 CICS Services Used

Service Used by Purpose

QUERY COUNTER LGWEBST5 Read counters without changing them
READQ TS / WRITEQ TS / DELETEQ TS Both Start marker, interval and rate queues

RETURN Both Task termination
EIB fields Both Diagnostic header

7.2 Definitions Required

  • Named counter pool GENA must be defined and active in the CICS region.
  • The counters themselves must exist. For example, GENACUSTNUM must be registered with that exact name, padded to 16 characters.
  • Transaction SSST must be defined in the CSD and mapped to LGWEBST5.
  • The event-processing adapter must be configured to start LGASTAT1 with the two DFHEP.DATA containers.
  • The include file LGCMAREA defines the shared COMMAREA structure used by LGASTAT1.

8. Constraints and Design Considerations

8.1 Data Size and Format

  • Counter values and accumulators in LGWEBST5 are FIXED BIN(31). This limits each to about 2.1 billion.
  • Rate values (NRATEVAL, ORATEVAL, DRATEVAL) are 9-digit pictures. Values above 999,999,999 lose their high-order digits.
  • Rate queue items are 9 bytes. The interval queue items are 6 bytes.
  • The queue name WS_TSQNAME is always 8 characters: the prefix GENA, then a 3-character code plus V, or X0nV.
  • FORMATTIME is assumed to return HHMMSSTH. The first 6 characters are used.

8.2 Table Dimensions

  • The loop bound of 17 is hard-coded. Adding an operation means updating CT_SUCCESS, CT_ERROR, CT_CODE, CT_OPS and the loop together.
  • Each CT_OPS character must be one of I, A, U or D. Otherwise the counter is left out of the sub-totals.
  • The CT_CODE values must be unique.

8.3 Sequencing

  • LGASTAT1 reads the containers before it considers the COMMAREA. It normalises the codes before GET COUNTER.
  • LGWEBST5 calls TRAN_RATE_INTERVAL before querying counters. It deletes each queue before rewriting it, so the three-item order is preserved.

8.4 Interval Behaviour

  • The interval is ABS(new − old). A midnight crossover therefore gives a large value. For example, 23:59:55 to 00:00:55 gives 86,340 seconds instead of 60.
  • On the first run the default previous time is 120000 (noon, 43,200 seconds). The first interval can therefore be anomalously large.
  • The one-minute restart delay is fixed in the source.

9. Error Handling

Both programs use RESP on their CICS commands and avoid abends. The failures they do handle give simple fallbacks. Most other failures are silently ignored.

Area Program Behaviour
Container read failure LGASTAT1 Falls back to the COMMAREA. Only the second read’s response is tested.
No COMMAREA (EIBCALEN = 0) LGASTAT1 Returns immediately without counting. This is the only validation exit.
Missing GENASTRT (QIDERR) LGASTAT1 Creates the queue with the current date and time.
WRITEQ TS failure Both Response not checked.
GET COUNTER failure LGASTAT1 Response not checked. A missing counter or pool is silently ignored.
Missing GENA000V LGWEBST5 Previous time defaults to 120000.
Missing rate queue LGWEBST5 ORATEVAL set to 0.
QUERY COUNTER failure LGWEBST5 Response not tested. A missing counter contributes the previous COUNTVAL, which is 0 initially.
DELETEQ TS failure LGWEBST5 Absorbed (for example, queue not found on the first run).
START failure LGWEBST5 Response captured only. The current cycle completes.

Neither program has PL/I ON-units, retries, logging or error messages. The only diagnostic aid is the working-storage header, which holds the eyecatcher, transaction ID, terminal ID, task number and COMMAREA length. It appears in dumps and traces but drives no decisions.

10. Examples

10.1 LGASTAT1: Successful Channel-Driven Increment

Input

  • Container DFHEP.DATA.00001 = 01ICOM, container DFHEP.DATA.00002 = 00.
  • Queue GENASTRT already exists.
  • Counter GENA01ICOM00 = 124.

Result

  • The containers are read successfully, so no COMMAREA is used.
  • No normalisation applies, and the counter name is GENA01ICOM00 .
  • GET COUNTER advances the counter from 124 to 125, and TRANCOUNT = 125.
  • GENASTRT is unchanged.

10.2 LGASTAT1: Failed COMMAREA Request with Queue Initialisation

Input

  • No containers. CA_REQUEST_ID = 02ACUS, CA_RETURN_CODE = 01, EIBCALEN = 32500.
  • GENASTRT does not exist, and the clock is 01/11/2023 14:15:30.
  • Counter GENA01ACUS99 = 45.

Result

  • The COMMAREA fallback is used.
  • READQ TS returns QIDERR, so the record 01112023 141530 is written to GENASTRT.
  • 02ACUS is normalised to 01ACUS, and 01 is collapsed to 99.
  • Counter GENA01ACUS99 goes from 45 to 46.

10.3 LGWEBST5: First Run

Input

  • Time 10:15:30. GENA000V and GENAX05V do not exist. GENACUSTNUM = 1500.

Result

  • The previous time defaults to 120000 (43,200 s). The current time is 36,930 s, so the interval is |36930 − 43200| = 6,270.
  • GENA000V holds item 1 = 101530 and item 2 = 006270.
  • GENAX05V holds 000001500, 000000000 and 000001500.
  • SSST is scheduled to start in 1 minute.

11. Operational Summary

The sequence below summarises how the two programs fit together in operation:

  1. Each business request that completes triggers LGASTAT1, which increments one GENA counter.
  2. The first event ever processed also stamps GENASTRT, which records when collection began.
  3. Once per minute, LGWEBST5 snapshots every counter. It sums the counters by operation type and writes the new, old and delta values to TS queues.
  4. A display or monitor can read those queues to show cumulative totals and per-interval throughput. Together with GENA000V it can also show the elapsed seconds between samples.
