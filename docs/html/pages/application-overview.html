Application Overview

The General Insurance (GenApp) application is an enterprise-grade z/OS system designed to manage core insurance operations, including customer demographics, multi-line policy administration, and claims processing. GenApp provides a hybrid transaction processing architecture, supporting interactive online interfaces (CICS 3270 BMS menus), modular business services, integration with business rules engines (Operational Decision Manager / ODM), and sequential batch processing for customer reporting.

1. Overview

GenApp manages the full lifecycle of general insurance products. It coordinates customer data and cross-domain policy types—Endowment, House, Motor, Commercial, and Claim—through standardized communication contracts.

The application architecture cleanly separates Presentation and Ingestion, Orchestration and Business Logic, Enterprise Business Rules, Diagnostic Logging, and Data Persistence.

The system is engineered around modular CICS programs linked via fixed 32,500-byte Communication Areas (COMM_AREA defined in LGCMAREA.inc). Orchestrators handle validation, routing, and diagnostic tracking, while delegating relational database operations directly to dedicated database subprograms.

2. System Architecture

GenApp follows a multi-tiered architecture that standardizes communication between online presentation, batch facilities, core orchestration, rule execution, and data access.

2.1 Layered Architecture Overview

  1. Presentation / Entry Tier:
    • CICS BMS Interface (LGTESTC1): Pseudo-conversational 3270 screen handler providing customer search, addition, and modification functions.
    • Batch Entry (LGBATCH): Non-CICS Enterprise PL/I batch utility that reads flat files (CUSTIN), coordinates database lookups, and generates report lines (CUSTRPT).
    • Environment Control (LGSETUP): CICS utility initializing application state, temporary storage queues, and named counter sequences.
  2. Business Orchestration Tier:
    • Modular CICS programs (LGICUS01, LGIPOL01, LGAPOL01) that enforce interface contracts, validate buffer sizes, manage routing logic, and format runtime diagnostics.
  3. Decision & Rule Processing Tier:
    • Externalized decision logic (LGAPBR01) integrated via conditional links to apply ODM validation on transactions such as endowment policy additions.
  4. Data Access & Persistence Tier:
    • Dedicated Db2 persistence programs (LGICDB01, LGIPDB01, LGAPDB01) executing embedded SQL against normalized relational entities.
  5. System Services & Diagnostic Infrastructure:
    • Shared logging routines (LGSTSQ), transient data/temporary storage queues (GENAERRS, GENACNTL, GENASTAT, GENASTRT), and CICS Named Counters (pool GENA).

3. Insurance Business Domains

GenApp manages two primary structural entities: Customers and multi-line Policies.

3.1 Customer Domain

Customers are the core entity in the GenApp suite. Each customer is assigned a 10-digit numeric customer number (PIC '9999999999').

  • Core Attributes: First Name (CHAR(10)), Last Name (CHAR(20)), Date of Birth (CHAR(10)), House Name (CHAR(20)), House Number (CHAR(4)), Postal Code (CHAR(8)), Mobile Phone (CHAR(20)), Home Phone (CHAR(20)), and Email Address (CHAR(100)).
  • Control & Allocation: New customer numbers are seeded and generated using CICS Named Counters (GENACUSTNUM in pool GENA) and recorded within boundaries tracked in the GENACNTL CICS Temporary Storage Queue.

3.2 Policy Domain and Product Types

Policies are linked to customers via a 10-digit customer number reference (CA_CUSTOMER_NUM). All policies share common administrative metadata, overlaid with specialized product fields within the LGCMAREA communication area.

3.2.1 Product Type Specifications

  1. Endowment Policies (POLICYTYPE = 'E'): Investment and life-coverage policies featuring profit flags (WITHPROFITS, EQUITIES, MANAGEDFUND), fund names, duration term (TERM), sum assured, and beneficiary names. Subject to ODM rules verification via LGAPBR01.
  2. House Policies (POLICYTYPE = 'H'): Real estate insurance defining property type, bedroom counts, structural replacement value, and property address attributes.
  3. Motor Policies (POLICYTYPE = 'M'): Vehicle insurance tracking vehicle make, model, valuation, registration number, engine CC capacity, manufacturing date, premium rate, and accident history count.
  4. Commercial Policies (POLICYTYPE = 'B'): Enterprise risk coverage containing geolocation data (latitude/longitude), peril categories (Fire, Crime, Flood, Weather), individual premium breakdowns, underwriting status, and rejection rationale codes.
  5. Claims Domain (POLICYTYPE = 'C'): Incident claims tracking claim identifiers, incident dates, amounts paid to date, claim estimated values, incident cause descriptions, and adjuster observations.

4. Online and Batch Entry Points

4.1 Online CICS Interactive Menu (LGTESTC1)

Online terminal interactions execute via transaction ID SSC1, managed by LGTESTC1:

  • Screen Mapping: Utilizes BMS mapset SSMAP (screen map SSMAPC1).
  • Pseudo-Conversational Design: Restarts via EXEC CICS RETURN TRANSID('SSC1') COMMAREA(COMM_AREA) to maintain transaction context across user entries.
  • Functions Supported:
    • Option 1 (Inquire): Populates COMMAREA with CA_REQUEST_ID = '01ICUS', links to LGICUS01, and renders customer profile details.
    • Option 2 (Add): Cleanses input data (translating 00'X nulls to spaces, uppercasing postcodes), sets CA_REQUEST_ID = '01ACUS', links to LGACUS01, and upon success updates high customer number tracking in GENACNTL via internal routine WRITE_GENACNTL.
    • Option 4 (Update): Performs a pre-inquiry via LGICUS01, awaits user field edits on a secondary RECEIVE MAP, sets CA_REQUEST_ID = '01UCUS', and executes update persistence via LGUCUS01.
  • Failure Recovery: Reverses failed additions using EXEC CICS SYNCPOINT ROLLBACK before alerting the operator.

4.2 Online Administration and Environment Setup (LGSETUP)

Triggered via transaction code LGSE (with an optional 10-digit high customer number parameter, e.g. LGSE 0000000500):

  • Clears and rebuilds four runtime temporary storage queues:
    • GENAERRS (runtime error queue)
    • GENASTRT (system startup metadata)
    • GENASTAT (transaction statistics records)
    • GENACNTL (customer number bounds: header, LOW CUSTOMER=0000000001, HIGH CUSTOMER=nnnnnnnnnn)
  • Initializes CICS Named Counter GENACUSTNUM in pool GENA to seed automated customer ID assignment.
  • Resets 36 distinct transaction-statistics counters tracking success (00) and failure (99) for all operations across customer and policy types.

4.3 Batch Customer Reporting (LGBATCH)

Non-CICS batch driver for offline reporting:

  • Opens sequential fixed-block dataset CUSTIN (RECSIZE(10)).
  • Dynamically loads (FETCH LGBATCHF) the line formatting subroutine.
  • Iterates through customer numbers in CUSTIN, executing singleton embedded SQL SELECT queries against the Db2 CUSTOMER table.
  • Converts status codes (0 → '00', 100 → '01', other → '90'), formats 80-character report records via LGBATCHF, and writes them out to sequential file CUSTRPT.
  • Handles file-open failures via an ON UNDEFINEDFILE(CUSTIN) unit that alerts the console and terminates with return code 16 via PLIRETC(16).

6. Communication Area and Data Contracts

Cross-program communication in GenApp relies on the shared 32,500-byte LGCMAREA layout overlaid across caller buffers.

6.1 LGCMAREA Structure Definition

DCL 1 COMM_AREA BASED(COMM_AREA_PTR),

      2 CA_RETURN_CODE         PIC '99',      /* '00'=Success, '98'=Len, '99'=Err */

6.2 Standard Return Codes

  • '00': Transaction processed successfully.
  • '01': Target record not found (Db2 SQLCODE 100 in batch lookups).
  • '90': Unhandled relational database / SQL error encountered.
  • '98': Communication area length validation error (supplied buffer shorter than minimum required length).
  • '99': Generic backend service error or fatal Db2 failure.

7.1 Fail-Fast Validation and Logging Pattern

If an orchestrator receives an empty communication area (EIBCALEN = 0), it generates a timestamped diagnostic record, links to the shared logging routine LGSTSQ, and abends immediately:

PL1 
/* Defensive Validation Pattern in LGICUS01 / LGIPOL01 / LGAPOL01 */
IF EIBCALEN = 0 THEN DO;
   EM_MSG_TEXT = ' NO COMMAREA RECEIVED';
   CALL WRITE_ERROR_MESSAGE;
   EXEC CICS ABEND
        ABCODE('LGCA')
        NODUMP;
END;

/* Internal Logging Routine */
WRITE_ERROR_MESSAGE: PROC;
   EXEC CICS ASKTIME ABSTIME(WS_ABSTIME);
   EXEC CICS FORMATTIME ABSTIME(WS_ABSTIME)
        MMDDYYYY(WS_DATE)
        TIME(WS_TIME);
        
   EM_DATE = WS_DATE;
   EM_TIME = WS_TIME;
   
   EXEC CICS LINK PROGRAM('LGSTSQ')
        COMMAREA(ERROR_MSG)
        LENGTH(STG(ERROR_MSG));
        
   IF EIBCALEN > 0 THEN DO;
      IF EIBCALEN < 91 THEN
         CA_DATA = LEFT(COMM_AREA_RAW, EIBCALEN);
      ELSE
         CA_DATA = LEFT(COMM_AREA_RAW, 90);
         
      EXEC CICS LINK PROGRAM('LGSTSQ')
           COMMAREA(CA_ERROR_MSG)
           LENGTH(STG(ERROR_MSG));
   END;
END WRITE_ERROR_MESSAGE;
